# Architecture Overview

> This page describes the current native logical/relocatable production path. The [Native Single-File Storage Re-architecture Plan](native-single-file-storage-plan) is the normative format and lifecycle contract. Legacy `DataManager`, segment-chain, external-WAL, and physical-executor material are historical migration references, not current architecture.

ZYX is an embeddable graph database engine. Its core is an in-process library — no separate server process is required.

**Layer responsibilities:**

- **Application Layer** — CLI tool, benchmark suite, and host applications that embed ZYX.
- **API Layer** — C++ API (`zyx.hpp`), stable Driver ABI (`zyx_driver_abi.h`), language bindings, and WASM bindings for browser use.
- **Query Layer** — Cypher text becomes a typed logical plan. The logical optimizer preserves semantics while applying bounded scan and row-window normalizations; logical read and mutation runtimes execute the plan through storage-neutral interfaces.
- **Storage Layer** — `RelocatableStorageBackend` owns one database file, pinned metadata snapshots, the canonical System Catalog, typed page stores, and native maintenance. `StorageIO` and the generation-aware Buffer Pool provide the typed I/O boundary; external WAL/SHM sidecars are not part of the production protocol.
- **Core Layer** — `Database` owns the backend and lazily initializes `QueryEngine` and the thread pool. `Transaction` owns a native logical transaction, its read-your-writes overlay, and its pinned lifetime.

## Main Execution Paths

### Query Path

```mermaid
sequenceDiagram
    participant App
    participant DB as Database
    participant QE as QueryEngine
    participant RT as Logical Runtime
    participant B as Relocatable Backend

    App->>DB: beginTransaction()
    DB->>App: Transaction (overlay and snapshot)
    App->>QE: execute("CREATE (n:User {name: 'Alice'})")
    QE->>QE: Parse → Logical Plan → Optimize
    QE->>RT: Execute typed logical operators
    RT->>B: Stage native graph mutation
    App->>App: tx.commit()
    Note over App,B: See Write Path below
```

### Write Path (commit)

```mermaid
sequenceDiagram
    participant TX as Transaction
    participant Overlay as Logical transaction overlay
    participant B as RelocatableStorageBackend
    participant M as RelocatableMetadataStore
    participant IO as StorageIO

    TX->>Overlay: validate final graph state
    Overlay->>B: plan bounded typed COW pages
    B->>IO: write candidate data and metadata pages
    IO->>IO: data sync fence
    B->>M: publish one complete metadata generation
    M->>IO: A/B Superblock sync fence
    M-->>TX: old-or-new visibility after reopen
    TX->>TX: retire overlay and release transaction resources
```

### Read Path

```mermaid
sequenceDiagram
    participant App
    participant TX as Transaction (read-only)
    participant B as Relocatable Backend
    participant M as Metadata Snapshot
    participant BP as BufferPool
    participant IO as StorageIO

    App->>TX: beginReadOnlyTransaction()
    TX->>B: open logical read snapshot
    B->>M: pin one metadata generation
    App->>B: resolve logical Node / adjacency / property
    B->>BP: read typed page by physical route and generation
    alt Cache hit
        BP-->>B: pinned page bytes
    else Cache miss
        BP->>IO: positioned typed-page read
        IO-->>BP: validated page bytes
    end
    B-->>App: logical result
```

## Design Principles

1. **Embeddable first** — ZYX is a library, not a server. Link directly into your process.
2. **Pinned snapshots** — every native read resolves data through one immutable metadata generation, so page relocation and reuse cannot mix generations.
3. **One-file COW publication** — candidate pages are durable before one A/B Superblock publication; reopen observes either a complete old or complete new generation.
4. **Typed, bounded I/O** — entity, property, index, Catalog, and Vector stores retain owner/generation/checksum validation and use finite cursors and admission-aware cache reads.
5. **Fail closed** — malformed routes, keys, checksums, ownership, generation, and resource bounds are rejected rather than falling back to a legacy representation.
