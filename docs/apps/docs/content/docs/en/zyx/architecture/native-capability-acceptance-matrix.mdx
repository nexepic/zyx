# Native Capability Acceptance Matrix

> This is the C0 ledger for the [Native Single-File Storage Re-architecture Plan](native-single-file-storage-plan). It is an acceptance record, not a list of aspirational features. A capability is `NATIVE_COVERED` when its public contract has a named native acceptance test; `IN_PROGRESS` records remaining final gates, while `HOLD_FOR_PORT` is reserved for a capability with an actually audited legacy owner or specification source.

## Status Vocabulary

| Status | Meaning | Deletion rule |
|---|---|---|
| `NATIVE_COVERED` | The native implementation and its public behavior have named acceptance evidence. | May be considered for retirement only after all dependent rows and three-platform gates pass. |
| `IN_PROGRESS` | A native route exists, but a contract, performance, transaction, recovery, or platform gate is incomplete. | Keep the native owner and its contract evidence; retain legacy behavior/tests only when an audit still identifies them as required specifications. |
| `HOLD_FOR_PORT` | The legacy tree still supplies behavior, tests, a public API, or a required consumer. | Never delete it. Port the behavior and test first. |
| `UNSUPPORTED` | Not part of the supported public contract. | Record the decision and remove only after C0 proves there is no public consumer. |

## Acceptance Record Rules

Every capability record must identify all of the following before a legacy source or test can be retired:

- the observable public contract, including results, errors, ordering, transaction visibility, and resource bounds;
- the storage-neutral native owner; no record may cite a physical Segment location as public identity;
- one or more named native test files that exercise the contract through the production source set;
- required platform, crash/recovery, performance, and four-dimensional coverage gates; and
- any legacy source/test family that remains a required specification until those gates pass; a retired family is not recreated merely because a final gate is open.

New Cypher clauses, functions, procedures, C++ API operations, Driver ABI operations, bindings, and administration commands add a row before implementation. A broad test-suite pass never substitutes for a named contract row.

## Completion Criteria

C0 is complete only when every supported individual clause, function, procedure, C++ API operation, Driver ABI operation, binding operation, algorithm, and administration command has a row at this level of precision. The Driver ABI resource-group ledger and current language-binding surface ledger are now exhaustive, and the C++ `QueryBuilder` and native-procedure sub-ledgers are also explicit checkpoints. The broader family-level ledger remains intentionally incomplete until Cypher clauses/functions, remaining C++ APIs, and algorithms receive equivalent records; it protects legacy specifications now, but does not authorize further deletion.
