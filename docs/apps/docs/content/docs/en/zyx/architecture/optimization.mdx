## 2. Facts, core hypothesis and evidence limits

The implementation already has typed columns, batch admission, certified ID borrowing, page reuse and shared field pages. Adding these names again is not new optimization. Medium score pages fell 3437→859 and group/score union pages 3443→1718 while an order-of-magnitude gap remains.

Current source shows a structural hypothesis: columns are located through owners and 64-owner groups, reorganized into small ordinal/value runs, copied through callbacks into query columns, then filtered. Relevant entries:

- `include/graph/storage/relocatable/property/HybridPropertyValueReader.hpp`: `readSelected` and `emitColumn` build group-local ordinals/words and split runs by type, missingness and NULL.
- `src/query/execution/DirectPropertyColumns.hpp`: `appendScalarRun` writes values/types/states/written markers and checks bounds and validity per cell.
- `src/query/execution/read_runtime/NodeSupplyAndSorting.inc`: receives supply, constructs/seals query columns, then filters.
- `src/storage/relocatable/property/property_read/SelectedColumnSupply.inc`: validates batch shape/order/snapshot and routes native/ROW representations.

**Hypothesis: storage has column representations, but execution contracts still require repeated location, rearrangement and materialization, charging simple analytical queries for several generic property layers.** This is not a current time attribution. If location or decoding dominates after removing intermediate materialization, follow that evidence rather than a predetermined design.

The former 63.97% supply boundary was measured before shared field pages and represents elapsed boundary attribution, not current CPU shares. Historical allocation counts are not current measurements. Kuzu EXPLAIN does not establish actual pruning or operator time. Do not conclude that64-owner groups, BTree or the entire backend is the root cause without evidence.

## 3. Objectives, scope and priorities

The final goal is to match or exceed Kuzu on all eight primary comparisons under equivalent semantics, resources and result consumption, with lifecycle and adoption costs validated. Report architectural milestones separately from Kuzu attainment.

Prioritize an end-to-end storage/execution column-block contract; next, proven expensive scan location and column-block directories; then typed filter/count/group consumption. R0 attribution determines implementation order; do not unconditionally rewrite all three layers.

Do not preselect larger logical groups, a new large-block format, replacement trees, LSM/WAL rewrites, JIT, SIMD or multithreading. Logical groups, physical pages, scan batches and operator batches are distinct. Changing scan granularity need not change persistent format. Expand scope only after evidence establishes a common foundational obstacle and this roadmap is explicitly revised.

### Decisions governing foundational changes

| Layer | First experiment | When to expand the change |
| --- | --- | --- |
| Scan planning | Pass safe predicates and required columns into scans; prune using statistics valid for the visible version | Scan fully when statistics are untrusted; choose persisted statistics and update maintenance only after establishing value |
| Storage reads | Scan windows spanning multiple 64-owner groups, sequential columns and block authentication while retaining logical group identity | Try a new physical column block or directory only if counters show unavoidable repeated page access/decoding that windows cannot remove |
| Execution | Typed blocks, selection vectors, late materialization, direct filter/count consumption and reusable typed grouping keys | Address planning, key construction or aggregation when attribution identifies dominant costs outside supply |
| Persistence/backend | Retain transaction, recovery, page-management and general fallback contracts | Replacing backend, tree or transaction framework requires evidence that local contracts cannot meet the goal, plus migration/write-amplification comparisons |

64 is a logical grouping granularity, not a requirement that all computation use that size. Decouple scan windows from logical groups before enlarging groups. Current evidence supports testing interface and access-pattern changes, not rebuilding the entire database.

### R1: minimal complete vertical experiment

Start with all-node numeric filter/count through the public API and normal snapshots. Operators should consume authenticated typed views or bounded decoded blocks directly, reducing intermediate rearrangement in `emitColumn → appendScalarRun → seal → filter`.

Specify types/encoding, row mapping, presence/NULL and selection bitmaps, snapshot/generation identity, buffer ownership, borrow lifetime, resource account, cancellation points, fallback and error propagation. No use after borrow expiry, replay after delivery or relaxed authentication/cancellation/budgets. Admission precedes allocation or delivery; amortization across blocks is permitted.

Use real persistent and updated data, not only an immutable in-memory array. Borrowed views or bounded decode buffers are both acceptable; disclose necessary copies for alignment, mixed types or lifetime constraints rather than pursuing a zero-copy label.

Also validate generic predicate pushdown and block pruning. Statistics must describe the visible snapshot and be safely maintained or invalidated after updates, deletion and type changes. Read any block that cannot be proven nonmatching; preserve NULL, missing, mixed-type, NaN and comparison-boundary semantics. Never depend on specific labels or distributions. Record candidates before/after pruning, skipped blocks, decoded values and statistics maintenance costs; cross-check results against the same path with pruning disabled. Block authentication must not rescan its certified set for every value, while preserving old-snapshot and cancellation correctness.

Exit requires complete result equivalence, affected boundary tests and deterministic proof that an entire class of rearrangement/copy/per-value management is eliminated or materially reduced without moving work elsewhere. Preserve failed experiments; do not hide unchanged work behind more caches.

### R2: general scan/operator integration

Extend the validated path to label filtering, group counts and multi-key grouping. Carry columnar inputs, selections and necessary late materialization through the pipeline instead of reverting to generic per-value objects at every boundary.

If location remains dominant, evaluate a sequential scan cursor or column-block directory so location/authentication scales mainly with blocks/pages. New directories are hypotheses, not presumed wins. Layout changes require write/migration/fallback costs; larger groups alone are not evidence.

If grouping dominates, measure key construction, hashing, comparisons, string representation and allocations before selecting an implementation.

Allocation sampling provides a concrete candidate: in `current-work/allocation-attribution.json`, 392 of 493 samples taken every 256 allocations in the multi-key query have PMR string growth immediately above the budget resource, followed by `appendDistinctUint64` in the caller stack, identifying key serialization as a concrete investigation point. The generic multi-key path in `src/query/execution/read_runtime/AggregateOperator.inc` constructs a string key for each row before group lookup. These are allocation samples, not time or byte shares; verify path coverage and cost before changing it. Evaluate typed composite keys and allocation-free temporary lookup, retaining owned keys for new groups and preserving NULL/type comparisons, collisions, resource budgets and fallback semantics. No fast paths keyed to the four query strings, label names or dataset contents.

Exit requires a common contract for all four query classes with dense/sparse, missing/NULL, mixed types, unordered/duplicate requests and complex-value fallback semantics. Report fast-path coverage and fallback rates, not only ideal branches.

### R3: lifecycle, writes and space

Run only relevant module tests for modified boundaries: old/new snapshots, repeated updates, deletion/label/type changes, complex/large values, read-your-writes, cancellation, budget refusal, reentrancy, exceptions, atomic publication, recovery, reopen, pin-release reclamation and actual physical space reuse. Never weaken oracles to pass.

Cover larger-than-cache working sets, sparse/skewed synthetic data and holdout not used to tune the new candidate. Existing holdout was already observed: disclose this, do not call it blind. Any fresh blind dataset must be frozen/sealed in R0, never selected after outcomes.

Measure open/authentication, conversion, maintenance, peak RSS, resource accounts, file growth, write amplification and retained versions; logical reclamation is not file truncation. The former candidate had edge-write bytes +5.95%/+8.97% and repeated write-latency regressions. Do not inherit exemptions. Isolate common-engine versus layout effects with same-engine/different-layout diagnostics where needed.

No full unit suite. Code files must stay within3000 lines and pass the source-size check. Preserve Linux/macOS/Windows and WASM contracts; unexecuted platforms are not passing results.

### R4: one formal window with explicit success/failure

After source and necessary tests stabilize, run current frozen ZYX/new candidate/Kuzu on two datasets and four primary queries. Three independent processes, three warmups and ten measured samples each, rotating engine order. Fix one thread, CPU affinity,64 MiB BufferPool,64 MiB ZYX query materialization,6 GiB address space and2 GiB file limits; preserve default query timeout and semantics. Record Kuzu settings and result consumption explicitly.

Validate every full result; report process medians and pooled P50/P95 without selecting best runs or dropping outliers. Do not subtract old cross-window times to claim gains. Share this window with guards/adoption costs; reproduce failures narrowly rather than rerunning full matrices until one passes.

Before exiting R0 and implementing R1, preregister meaningful intermediate gain thresholds, stability rules and budgets supported by the cost model, constraining both overall geometric mean and all-node filtering on each dataset. If the model cannot support a substantial improvement, revise the design instead of substituting an arbitrary smaller gain.

The intermediate gain gate is preregistered in `benchmarks/architecture-design/decisions/20261027-column-block/intermediate-gates.json`: against the concurrent current control, require at least 1.5x geometric-mean speedup across eight primary P50s and at least 1.5x on each dataset’s all-node query; both pooled P50 and the median of three independent-process P50s must meet each gate. This is a target, not a prediction or a replacement for the eight-query Kuzu condition.

**The fixed final100% performance condition is candidate P50 no higher than Kuzu on all eight primaries. Candidate P95 over Kuzu by more than5% requires review; unresolved reproducible material tail regressions prevent acceptance.** Also review greater-than5% P50/P95, RSS or file-cost regressions against current ZYX for primaries, point/full-entity/adjacency reads, actual property updates, no-ops and edge batches. Fix reproducible material regressions or apply explicit restrictions within the adoption scope frozen before implementation; do not shrink scope after measurement to manufacture100%.

If Kuzu conditions fail, report actual gains, remaining gaps and stage progress with R4 incomplete. Do not reuse the former convention of100% for a finished plan with an unmet performance target. Preserve failures and revise this roadmap from evidence before another registered candidate; no indefinite unregistered candidate sequence.
