# Batch Scan Path Architecture Optimization Plan

Updated: 2026-10-23. Plan ID: `scan-path-20261023`. **This is the sole active checklist for the next round, focused on the highest-priority batch scan bottleneck. Implementation progress is 15%; editing the plan and historical diagnostics do not count as implementation progress.**

The previous incremental commits, import work and experimental cold conversion are complete and are removed from the active queue. Historical acceptance remains in `benchmarks/architecture-design/decisions/20261023-core-cost-acceptance/`. Historical implementation completion does not establish read-performance acceptance. Do not reintroduce old P1–P7 tasks, stage reports or experimental capability lists as additional work.

## 1. Objective and scope

One workstream: **connect candidate generation, entity/label validation, property reads and operator consumption into an efficient end-to-end batch scan path**. Preserve the general property graph and reduce repeated per-entity work. Do not specialize on query text, label names, fixed properties or benchmark distributions.

Cover label filters, untyped property filters, actual single-/multi-key grouping and their shared projection/property supply. The objective is to substantially reduce the Kuzu gap. The default adoption gate requires at least 5x speedup for each of the four primary workloads on both medium and holdout against the frozen starting point. This prevents local-only improvements from proceeding to full implementation; it is not a promised result. Report superiority to Kuzu separately for every workload.

**Out of scope:** independent bulk-import redesign, ordinary transaction optimization, vector dimensions, radix/B+Tree replacement, general caching, WAL/LSM, JIT, additional threads and whole-backend replacement. Existing import only prepares real frozen inputs. Updates, recovery and maintenance required by the selected read representation are in scope; a new COPY product entry point is not.

- Label workloads still process 100,000 property roots in 196 batches. The all-node filter processes 225,000 roots in 440 batches and delivers 220,000 numeric fields. Direct typed columns and runs already operate; adding a batch API is not a new optimization.
- Label workloads have one property-directory refill and reuse their cursor. They do not restart the entire directory tree for each entity. Per-entity record-header, identity, offset-directory and field-selection work remains.
- Warm query windows are CPU dominated. Disk waiting is not the leading supported explanation; hardware cache/TLB counters were not measured, so CPU memory stalls remain possible.
- The three supply stages account for about 86% of label-filter/single-key-group samples. Eliminating the filter's 42.6% property-supply cost with everything else fixed gives only about 1.74x theoretical speedup. A column layout alone is insufficient if the other supply stages remain.
- Stages include downstream callbacks and allocations, not just decoding or I/O. The remaining bucket is not all aggregation work. Each workload has one control/sampled process pair, for coarse attribution; about 13–17% of read samples are unresolved libc leaves and must not be assigned invented callers.
- Kuzu EXPLAIN shows node-table scans of required properties, without extra property-index operators. EXPLAIN does not establish actual zone-map skipping. New profiling primarily covers medium; holdout timings remain the historical formal measurements, not a new holdout profile.

## 3. System contracts to preserve

- Preserve dynamic properties, multiple labels, stable logical IDs, missing versus NULL, type changes, complex values and LargeValue, plus Cypher, transaction, Driver ABI, binding and operator semantics.
- Preserve strict single-file storage, COW, A/B Superblock, data-before-root, durable acknowledgement, read-your-writes, old snapshots, cancellation, unified resource budgets and safe reclamation. Do not disable synchronization, cancellation or validation for speed.
- Retain the user-approved local-access validation plus complete integrity contract: validate accessed pages/new paths; discover unrelated corruption on first access or full inspection. Reused validation must bind immutable physical versions, generation, snapshot and applicable I/O epoch, not logical ID or pointer alone.
- Field blocks/memory views must not form an unaccounted second database. Account for durable/transient/index/old-pin/maintenance costs separately. Do not silently increase cache, query-memory or temporary-space limits.
- Preserve macOS/Linux/Windows and WASM compatibility; list platforms actually tested. Linux diagnostic observers stay outside portable production code.
- Update the [storage specification](native-single-file-storage-plan) before a format change, documenting versions, old-file reading/rejection, explicit conversion and failure fallback. Never overwrite users' original files or bypass existing experimental whole-database space, peak or atomicity gates.

## 4. Architecture direction and selection boundaries

These are design requirements, not implemented APIs. S1 records a decision; S2 validates it before full lifecycle implementation.

### 4.1 One logical model and one batch access contract

- Separate stable logical IDs from physical placement. Bounded groups are not fixed label tables. Multiple labels must not duplicate logical entities, and type changes must not become schema errors.
- The batch contract carries entity IDs/order, visibility, label membership, column types, missing/NULL masks, required selection sets and borrowed-data owner/version/lifetime.
- Establish shareable identity, visibility and field-location proofs at block/batch boundaries. Keep necessary per-value type/range/semantic checks. Certified membership must publish atomically with creation, deletion, label changes and recovery.
- Use one entry for filtering, projection and actual single-/multi-key grouping; no shadow executor for COUNT or fixed fields.
- Feed the existing typed batch interface. Primitive values must not rebuild generic PropertyValue matrices or per-row property maps. Define and count fallback costs for complex/mixed/missing values.

### 4.2 At most two candidates; do not assume columns win

Compare two bounded candidates: A, reusable block/batch location and validation views over current ROW; B, persistent typed blocks for stable dense fields, with general representations for sparse/complex properties. Both must connect candidate generation and entity validation. Comparing a bare in-memory array with a complete production query is invalid.

Audit existing experimental layouts against the batch contract, adoption coverage and total costs before reuse. Existing code is not a selection criterion. Width, type stability, density, update rate and observed access costs drive selection, never `User`, `country`, node counts or query text. Freeze selection rules before holdout validation.

### 4.3 Updates and maintenance are part of read design

First evaluate local block COW. Compare a bounded update layer only after proving unacceptable small-update write amplification; do not automatically add a logging/LSM subsystem.

S1 must specify per-block entity/byte bounds, maximum merge depth per read, change precedence, type changes/demotion, reorganization triggers, temporary-space limits, old-pin retention, cancellation points and budget-denial behavior. Derive and register numeric limits from existing resource contracts and frozen scale; do not leave them unspecified or unbounded under an adaptive label.

Publish fields, membership and primary data atomically. Failure, cancellation or crashes must not expose a conversion prefix. Relocation/reclamation reuse version and ownership mechanisms; an independent cache cannot hide consistency issues. Keep ROW when conversion is uneconomic, with observable refusal reasons. Do not relax space gates to force benchmark adoption.

Weights measure accepted deliverables, not code volume or performance attainment. Dependency order: S0 → S1 → S2 → S3 → S4 → S5. S0/S1 are accepted; S2–S5 are unaccepted. Documentation, synthetic microbenchmarks and experimental entry-point functionality do not replace production-path acceptance.

### S0: Freeze once, without reopening the full matrix

Register formal inputs/oracles, source/library SHAs, Kuzu version, thread count, cache/memory budgets, compiler options and platform. Medium has 225,000 nodes/860,000 edges; holdout has 163,000 nodes/772,000 edges. Reuse accepted input hashes, not newly generated favorable data.

Reuse formal baselines and current diagnostics. Calibrate only when environment/input/build identity cannot be matched. Preregister four primary workloads, oracles, the 5x adoption gate, guards, statistics and resource/space admission. The baseline is the default production path. Experimental layouts must report actual conversion/adoption coverage; do not discard refusals to claim whole-workload gains.

### S1: Produce a reviewable design first

Write a bilingual decision covering layout/identity/ownership, batch validation, logical/physical scan selection, missing/NULL/mixed types, updates/recovery, relocation/reclamation, budgets, complexity and migration. Identify work removed and work still required per entity.

Separate block/page/entity/field work in the cost model. Account for candidates, entity/property-root visits, field bytes, metadata reads, validation, allocations and batches per query. Distinguish complexity improvements from constant-factor reductions. Do not claim general scans can avoid all value comparisons.

### S2: Bounded selection; insufficient gains stop at this gate

Connect candidates → visibility/membership proofs → field batches → existing filter/group operators → owning outputs on real persistent data. Include reads after updates and reopen. Time the actual production chain; report conversion/build/maintenance separately rather than hiding them in preparation.

Run one bounded comparison window with at most two candidates. Allow one targeted correction/recheck for a demonstrated implementation bug. Develop on medium, freeze rules, then evaluate holdout. Require each primary workload on each dataset to improve at least 5x while satisfying semantics, resource and space contracts. If both candidates fail, retain unresolved-cost evidence and leave the stage unaccepted with a bounded design revision. Do not automatically expand into unrelated optimization or lower the gate.

Do not implement the entire migration/maintenance framework at this stage. Passing establishes that the design merits implementation, not production safety; S3 must complete the lifecycle.

### S3: Complete the production lifecycle

Implement one selected public batch access path and remove abandoned candidate branches. Record default/experimental/fallback/conversion eligibility so future production inputs can actually use it. A benchmark-only installer is not delivery.

Complete insertion/deletion, property addition/removal/type changes, label changes, transaction overlays, old snapshots/read-your-writes, LargeValue/complex fallback, local update/demotion, reorganization, reopen, A/B recovery, field/membership consistency, relocation and post-pin reclamation. Specify the format and explicit conversion entry; avoid permanently duplicating transaction or query semantics.

### S4: Validate generality and total cost

Run only affected module unit tests and necessary integration cases, never the full unit suite. Test semantic/failure boundaries rather than assertions mirroring implementation.

- Queries: empty input, all/no matches, missing/NULL, mixed numeric/text types, NaN/overflow, empty/embedded-NUL strings, long values, multi-key tuples and duplicates.
- Lifecycle: the updates above, old pins, cancellation, budget/conversion refusal, partial/complete root-write failures, recovery and full integrity.
- Generality: preregister at least one different density/width/type-distribution and overlapping-label input in S0. Include update-heavy and sparse data, plus working sets larger than the configured cache budget. Do not select inputs after observing wins or call cache-budget pressure physical cold-disk testing.
- Total cost: record queries, point/adjacency reads, SET, 1000-edge writes, conversion and maintenance separately. Include every structure, old version and auxiliary index in memory/steady/peak disk accounting. Preserve existing space/resource limits.
- Performance guards: retain point/full-entity/adjacency/large-value/write cases under equivalent conditions. Explain and fix stable P50/P95 regressions above 5%. Alternate baseline/current repeats only for suspect cases, retaining original results rather than deleting slow samples.

### S5: One final unified acceptance

After code and necessary tests are frozen, run the registered matrix once, not every round. Preserve semantics, threads/budgets and warm-cache definitions. Use three independent processes with three warmups and ten measured samples each; report per-process/pooled P50/P95, samples, failures and N/A. Do not repeat the full matrix without material new changes.

Report starting/final ZYX and equivalent Kuzu, result oracles, candidate/entity/property-root/batch work, CPU/wait boundaries, adoption coverage, build/maintenance costs, steady/peak space and tested platforms. Never sum nested timers, present sizeof sums as DRAM traffic, or treat process RSS high-water/file polling as exact peak allocation.

Allow 100% only when each primary workload on both datasets reaches 5x, S3/S4 are complete and no stable regression remains unresolved. Report Kuzu superiority separately and disclose unmet comparisons. A failed final performance gate leaves S5 unaccepted; code completion alone cannot produce 100%.

## 6. Execution discipline and stop conditions

Update accepted stage status each round and report the sum of accepted weights, actual gains and blockers. Commit/push to remote `work` only when the progress percentage increases. Draft designs, failed candidates and diagnostics do not inflate progress; no increase means no commit/push. S0 identity/oracle verification and the S1 design contract are accepted; progress is 15%. Evidence: `benchmarks/architecture-design/decisions/20261023-scan-path-s0/` and `benchmarks/architecture-design/decisions/20261023-scan-path-s1/`. S1 `design.en.md` and `contract.json` define the two candidates; the persistent candidate requires a complete wire specification before write implementation. No new scan implementation or performance gain is claimed, and S2 remains unaccepted.

Stop after S5 and final delivery. Do not automatically start import, ordinary-write or other optimization. When selection fails, preserve failure evidence and concrete blockers instead of expanding alternatives indefinitely. Any scope, resource-contract or acceptance-gate change must explicitly record its reason and the user's decision, never silently redefine completion.
