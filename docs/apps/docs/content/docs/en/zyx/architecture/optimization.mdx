## 1. Objective and scope

One workstream: **connect candidate generation, entity/label validation, property reads and operator consumption into an efficient end-to-end batch scan path**. Preserve the general property graph and reduce repeated per-entity work. Do not specialize on query text, label names, fixed properties or benchmark distributions.

Cover label filters, untyped property filters, actual single-/multi-key grouping and their shared projection/property supply. The objective is to substantially reduce the Kuzu gap. On 2026-10-26 the user explicitly removed the fixed 5x requirement. Selection now uses real end-to-end gains on both datasets against both same-machine controls, complete semantics and the unchanged resource/space contracts. Historical failed-gate evidence is preserved. Beating Kuzu remains the objective and must be reported separately; selection acceptance does not establish superiority.

On 2026-10-26 the user further clarified that completing this roadmap is sufficient for delivery; beating Kuzu is not a current completion requirement and the remaining gap may be optimized later. Report roadmap delivery separately from performance maturity. Never label known regressions as passes or expand this round indefinitely to catch Kuzu. Experimental-format adoption must account for scan gains, conversion cost, and point/write costs; the default ROW format is not automatically migrated.

The user's latest execution instruction overrides stage timing order: one initial ZYX/Kuzu calibration is complete; implementation now runs necessary module tests without further performance tests. Combine S2 candidate comparison and S5 comprehensive timing into the final window after all optimization code and necessary tests are complete. Do not accept S2 or adopt a default production path before performance evidence; required lifecycle implementation may continue in the isolated experimental format. Fixed weights, two candidates, adoption gates, resource limits and frozen holdout rules remain unchanged.

**Out of scope:** independent bulk-import redesign, ordinary transaction optimization, vector dimensions, radix/B+Tree replacement, general caching, WAL/LSM, JIT, additional threads and whole-backend replacement. Existing import only prepares real frozen inputs. Updates, recovery and maintenance required by the selected read representation are in scope; a new COPY product entry point is not.

### 2.2 Priorities expressed as work to eliminate

These priorities belong to one scan chain, not unrelated tuning projects. CPU shares locate costs; end-to-end measurements establish gains.

| Order | Work that must change | Implementation boundary and evidence |
|---|---|---|
| First | Reduce per-entity property-root location, header/offset parsing and field delivery | Reuse certified locations within one snapshot; supply stable typed fields by block to existing typed columns. Count root visits, parsing, fallbacks and allocations, not just batches |
| Required in the same stage | Reduce candidate generation followed by repeated entity liveness/label checks | A reuses valid batch proofs; B produces IDs and label selections from certified membership blocks. Cover property-less nodes, overlapping labels and deletion; existing field-group live masks are not complete entity membership |
| After selection | Complete transactions, recovery, reclamation and adoption on ordinary inputs | Publish under one atomic root; test updates, old snapshots and reopen without a separate consistency mechanism |
| Last | Evaluate remaining consumer costs and regression guards | Reassess residual costs on the new supply chain. Without new evidence, do not start aggregation rewrites, tree replacement or general caching projects |

Memory holds budgeted batch buffers and short-lived snapshot-bound views; existing caching and COW manage persistent membership/field blocks. Do not hide storage costs through whole-database expansion at startup, resident property replicas or unbounded certification tables. Current evidence supports changing scan representation and access boundaries; it does not establish a need to replace radix/B+Tree, the entire storage engine or transactions.

## 3. System contracts to preserve

- Preserve dynamic properties, multiple labels, stable logical IDs, missing versus NULL, type changes, complex values and LargeValue, plus Cypher, transaction, Driver ABI, binding and operator semantics.
- Preserve strict single-file storage, COW, A/B Superblock, data-before-root, durable acknowledgement, read-your-writes, old snapshots, cancellation, unified resource budgets and safe reclamation. Do not disable synchronization, cancellation or validation for speed.
- Retain the user-approved local-access validation plus complete integrity contract: validate accessed pages/new paths; discover unrelated corruption on first access or full inspection. Reused validation must bind immutable physical versions, generation, snapshot and applicable I/O epoch, not logical ID or pointer alone.
- Field blocks/memory views must not form an unaccounted second database. Account for durable/transient/index/old-pin/maintenance costs separately. Do not silently increase cache, query-memory or temporary-space limits.
- Preserve macOS/Linux/Windows and WASM compatibility; list platforms actually tested. Linux diagnostic observers stay outside portable production code.
- Update the [storage specification](native-single-file-storage-plan) before a format change, documenting versions, old-file reading/rejection, explicit conversion and failure fallback. Never overwrite users' original files or bypass existing experimental whole-database space, peak or atomicity gates.

## 4. Architecture direction and selection boundaries

These are contracts registered in S1 and awaiting S2 validation, not delivered production capabilities. Complete lifecycle implementation follows S2 validation.

### 4.1 One logical model and one batch access contract

- Separate stable logical IDs from physical placement. Bounded groups are not fixed label tables. Multiple labels must not duplicate logical entities, and type changes must not become schema errors.
- The batch contract carries entity IDs/order, visibility, label membership, column types, missing/NULL masks, required selection sets and borrowed-data owner/version/lifetime.
- Establish shareable identity, visibility and field-location proofs at block/batch boundaries. Keep necessary per-value type/range/semantic checks. Certified membership must publish atomically with creation, deletion, label changes and recovery.
- Use one entry for filtering, projection and actual single-/multi-key grouping; no shadow executor for COUNT or fixed fields.
- Feed the existing typed batch interface. Primitive values must not rebuild generic PropertyValue matrices or per-row property maps. Define and count fallback costs for complex/mixed/missing values.

### 4.2 At most two candidates; do not assume columns win

Compare two bounded candidates: A, reusable block/batch location and validation views over current ROW; B, persistent typed blocks for stable dense fields, with general representations for sparse/complex properties. Both must connect candidate generation and entity validation. Comparing a bare in-memory array with a complete production query is invalid.

Audit existing experimental layouts against the batch contract, adoption coverage and total costs before reuse. Existing code is not a selection criterion. Width, type stability, density, update rate and observed access costs drive selection, never `User`, `country`, node counts or query text. Freeze selection rules before holdout validation.

### 4.3 Updates and maintenance are part of read design

First evaluate local block COW. Compare a bounded update layer only after proving unacceptable small-update write amplification; do not automatically add a logging/LSM subsystem.

S1 freezes at most 512 entities per batch, 1 MiB each for source workspace and encoded block, and 64 typed fields and 64 labels per block. Preserve general semantics beyond these limits without truncation: fields use existing fallback; oversized label groups now retain complete live bits in explicit versioned records and reread complete primary labels when predicates need them, as specified in the latest S2 checkpoint. Persistent merge depth is one. Each maintenance operation handles at most one block with an 8 MiB workspace. Source workspace is also capped by the caller’s remaining query budget; old pins retain versions until safe reclamation. See S1 `contract.json` for the complete contract; adaptive behavior must not exceed these limits.

Publish fields, membership and primary data atomically. Failure, cancellation or crashes must not expose a conversion prefix. Relocation/reclamation reuse version and ownership mechanisms; an independent cache cannot hide consistency issues. Keep ROW when conversion is uneconomic, with observable refusal reasons. Do not relax space gates to force benchmark adoption.
