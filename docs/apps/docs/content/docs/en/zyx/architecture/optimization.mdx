## 1. Scope, decisions and document authority

### 1.1 Established boundaries

- Continue using **COW and A/B Superblocks**. Do not introduce WAL or treat cross-transaction group commit as ordinary tuning; changing commit acknowledgement requires a separate protocol design.
- Remain a general-purpose, embedded, strictly single-file database. Durable data, recovery information and query spill space belong to the same database file; no database WAL/SHM/temporary sidecars.
- Preserve stable EntityId/PageId, logical/physical separation, snapshots, read-your-writes, shared allocation, relocation, snapshot-safe reclamation, explicit codecs, integrity checks and public API/Driver ABI boundaries.
- Preserve clause IR, Expression, logical plans and useful caches/selected reads/batches. Do not revive retired storage or physical executors, or create a second complete database backend.
- **A3 authorizes layout design and admission experiments, not unconditional columnar replacement. A4 must establish its consistency protocol before selecting the physical layout.**
- LLVM is a conditional experiment, not a mandatory dependency. Establish efficient non-JIT execution first; retain a non-JIT WASM path.
- No query-text, dataset-name, fixed-answer or benchmark-size special cases. General cost models may use actual cardinalities, types, bytes, pages and selectivity.
- Preserve macOS/Linux/Windows portability; this assessment executes in Docker Linux ARM64 on a macOS host. **Run only relevant module unit tests, never the full unit suite; coverage is not a gate; no commit or push.** Generic repository templates and historical records do not override this scope.

## 2. Current facts and benefit hypotheses

The current pipeline includes QueryAST, Expression, LogicalOperator and LogicalPlanOptimizer. Logical runtimes directly execute plans; the main row representation still uses string-keyed hash maps. EntityRef delayed materialization, selected property reads, selection vectors and bounded batches already exist and must not be reimplemented as new features.

Properties are organized as owner collections; ordinary mutation requests replace complete collections, and large collections may be encoded into a single LargeValue payload. Ordinary adjacency is a global key-only B+Tree; obtaining neighbors/type generally requires Edge records. Ordinary write transactions use graph-root fences, which are safe but can conflict on disjoint writes. Sort has memory bounds; that does not establish general spill execution.

## 3. Architecture work packages A1–A7

Every design deliverable includes current call paths, target interfaces/ownership, data/snapshot identities, failure states, byte layouts/versions where applicable, recovery/reclamation states, replacement boundaries, module tests, benefit hypotheses and falsification conditions. The following contracts are mandatory; exact ABI/codecs, block sizes and cost parameters must be settled in S1 decision records, not guessed during coding.

This page specifies implementation direction and design admission, not a proven final architecture. S1 must record concrete decisions, evidence or explicit follow-up experiments for the questions below. Unresolved correctness and core-interface questions must close before the corresponding production implementation. Preserve directory layers with distinct responsibilities and bounded costs; reducing layer count is not itself a refactoring objective.

### A1: Bound execution representation and physical plans

Keep the frontend and logical IR. Add execution binding/physical planning after them. Resolve names to slots; property tokens/descriptors have explicit schema epochs and plan-cache invalidation. Use typed kernels for known types and semantically equivalent fallbacks for dynamic/mixed values.

Execution batches carry typed columns, presence/null information, selection vectors, EntityRefs and variable-payload owners. Define borrowing, batch reuse, page pins, ordering and multiplicity. Physical plans select access paths, join/aggregate/sort algorithms, pipelines and blocking materialization. Start with non-JIT scan/filter/project/aggregate; then migrate join, sort, unwind, procedures/subqueries and mutation read sides. These paths must not silently fall back to unaccounted old row objects.

Create owning QueryResult/Driver ABI values at the output boundary. Enumerate transitional adapters and their removal conditions; do not retain two independently maintained query semantics. Preserve NULL, numeric/type behavior, optional matches, paths, correlated subqueries, cancellation and public error behavior.

**Graph intermediate-result contract:** typed batches alone do not establish efficient graph execution. S1.1 must decide how to represent shared parent bindings, child-result groups and multiplicity, which operators consume grouped/factorized results, and where flat expansion is required. Define DISTINCT, aggregation, OPTIONAL, correlated subqueries, paths, final output and ownership; never treat correlated branches as independent Cartesian products. The first implementation may use flat batches, but must specify concrete adapters and extension boundaries rather than making fully expanded rows the only operator contract. Representative branching/multi-hop prototypes decide actual factorization adoption; copying all Kuzu join algorithms is not required, and this issue does not explain the entire gap in scans without joins.

**Execution-state contract:** distinguish immutable physical plans, query-shared state, task-local cursors/batches/aggregation state, and blocking-operator merge state in A1. Assign cancellation, errors, snapshot pins, budgets and output ordering explicitly. Initial execution may be single-threaded, but task state must not be an implicit singleton or inseparable operator state. O7 selects parallel implementation and scheduling granularity, not the initial state separation. S1.1 delivers state/lifetime tables and interface boundaries without requiring an early thread pool or scheduling framework.

### A2: Property patch contract

Support internal per-key set/remove while retaining explicit whole-map replacement. Preserve distinct semantics of single-key SET, map merge, full map replacement and REMOVE. Coalesce final durable state without changing intermediate statement overlay/read-your-writes behavior; never borrow LargeValue references past their lifetime.

Compute index, constraint and statistic changes only for affected fields. Define create-then-delete, no-op values, property deletion, type changes, conflicting index keys and final failure. Publish properties, derived indexes, statistics and entity state in one COW publication.

A2 may initially use the current layout. A request containing one field does not prove localized physical writing; measure interface and physical behavior separately.

### A3: Grouped and chunked properties for general graphs

**Goal: improve cross-entity narrow scans while preserving point reads, small updates, dynamic properties and full-entity retrieval. Do not unconditionally make all properties dense columns.**

1. Organize bounded entity ranges/slots into groups, with separate Node/Edge identity spaces. Stable EntityId is distinct from internal slot; deletion/reuse has generation/liveness metadata. Labels are membership, not duplicate property ownership; adding labels must not move entire entities.
2. Identify property chunks by PropertyKey/token. Dense fields use compact arrays/bitmaps; sparse fields use ordered slot/value pairs or compact presence/rank structures. Preserve mixed types and missing-property semantics; one observed value does not establish a permanent schema.
3. Support direct entity/field lookup and enumeration of fields actually owned by an entity. Full-node reads must not scan global property tokens or the whole group. Include routing/enumeration metadata in space/read/COW costs; do not create an independent tree for every entity-property pair.
4. Large values use independent LargeValue references; ordinary variable values use bounded local payloads. Define group, compression block, page and update unit separately. Changing one value must not rewrite an entire group or unrelated large values. First evaluate direct page-level COW updates; do not preselect multi-level deltas/LSM, hot/cold migration or automatic layout switching.
5. Each logical property has one unambiguous authoritative version per snapshot. If column chunks and sparse extensions coexist, the group descriptor determines ownership; extensions are not a second full copy. Layout transitions and retirement share a recoverable protocol.
6. Preserve snapshot/owner/generation checks. Define old-version reachability for group splits, slot reuse, large-value replacement, failed publication, relocation and whole-group deletion. Start with few encodings. Thresholds derive from general space/access costs, not benchmark names or special sizes.

S1.3 must provide access-path/cost tables for single-entity single-field reads, complete entities, cross-entity narrow scans, single-field changes and deletion/reclamation. Identify directories/descriptors/data pages traversed and pages copied by COW. Account separately for routing, field enumeration, presence/type, allocation and index metadata. Express cost growth with entity count, actual property count, distinct fields and page size, then verify page/byte counts experimentally. Do not count only value payloads or hide scan gains behind an expensive new membership directory.

Admission must also cover randomly interleaved entity shapes, insertion order unrelated to labels, many singleton fields, sustained type changes and sparse groups after deletion. Define metadata growth bounds, split/re-encoding triggers and worst-case foreground work. Compare complete-entity retrieval and local-update costs against the current layout. Retain the current layout when no candidate is acceptable; a columnar label does not establish superiority.

**Admission sequence:** establish a current-row-layout control, implement a complete lifecycle prototype, then decide on adoption. Before reusing old prototype readers, finish graph routing, index maintenance, unreachable child/root/LargeValue retirement, reopen and failed-publication recovery. A laboratory carrier is not a production engine.

Required cases: single/multi-field range scans, random single-field/full-entity reads, neighbor property gathering; sparse/dense fields, mixed types, multiple labels, wide entities and large values; set/remove/type changes, ingestion, deletion, long snapshots and sustained updates. Measure end-to-end latency, read/write bytes, peak memory and steady-state space. Resolve material point-read/update regressions or explicitly establish product tradeoffs; average scan improvements cannot hide them.

If the prototype fails Section 6 admission, reject that prototype, retain production format, record attribution and a revised proposal. Production milestones in S3 remain incomplete. Do not silently skip A3 to reach 100%, and do not ship a regressing layout merely to execute the checklist.

### A4: Direct adjacency access and trusted derived layouts

Logical batches provide EdgeId, NeighborId, TypeId and required visibility information, preserving direction, parallel edges, self-loops, type filters, continuation and overlay semantics. Authoritative Edge records define identity/topology; covered data is a protocol-maintained derivative, not independently writable authority.

First specify when authenticated adjacency fields can be trusted directly, checks performed at load/publication/integrity scan, missing-membership detection, and corruption/wrong-generation/inconsistency errors. Do not remove primary-record rechecks before proving the replacement contract; a checksum alone does not establish index/entity consistency.

S1.4 delivers a fault model and validation-responsibility table separating page byte/format/identity checks, transactional atomic maintenance and cross-structure integrity checks, with guarantees and detection times. Cover torn writes, wrong owner/generation, inconsistent covered fields and missing membership; do not promise that local reads detect every global inconsistency. If atomic maintenance establishes consistency and queries trust covered fields within valid snapshots, specify prerequisites and integrity-scan duties. Changes to detection timing relative to current per-entry rechecks must appear in public contracts, specifications and fault tests. Preserve current behavior until the replacement is admitted.

Compare two candidates behind one interface: covering entries in shared Packed B+Trees, and multi-node segmented adjacency blocks organized by direction/type. Both require shared space for low-degree nodes, supernodes, online changes, atomic bidirectional maintenance, relocation and reclamation. Avoid per-node roots/dedicated tail pages. Do not add public endpoint/type mutation solely for tests when current APIs do not support it.

Prefer the smaller covering-tree change if it meets goals. Adopt segments only when benefits justify maintenance/write amplification. Include topology-only traversal, typed expansion, multiple hops, random insertion/deletion, skewed degrees, self-loops/parallel edges and long-term space, not just sequential loading. Existing key-only files retain semantics until the format changes.

### A5: Isolation and conflict granularity

Derive the promised isolation level from public contracts/tests; do not automatically claim serializability. Define transaction snapshots, read dependencies, entity/property write intents, uniqueness/range/predicate dependencies and schema epochs. Specify phantom/write-skew behavior for the chosen level; write-set checks alone do not establish serializability.

Disjoint changes should not fail solely because graph roots changed. Detect overlapping writes, constraint conflicts and node deletion versus edge creation. After validation, rebuild candidates against current roots and publish atomically. A serialized publication gate is acceptable; stale page pointers must never overwrite newer versions. Define ID leases, retries, overlays, indeterminate commits and resource release. Do not merely delete the global fence.

S1.5 must specify the promised isolation level, allowed/forbidden concurrent outcomes, conflict keys, validation timing, retry boundaries and validation cost. Do not relax production fences before these decisions or silently weaken existing guarantees. Distinguish logical read/write conflicts from physical page sharing: disjoint entities/fields can occupy one COW page. Define rebuilding/merging against the latest version or conservative rejection, never overwriting another transaction's changes. Validate two-transaction interleavings for uniqueness, endpoint deletion, write skew, range reads and disjoint writes sharing a page.

### A6: Resource ownership and single-file spill

Unify query/batch/operator budgets, pins, variable payloads and cancellation. Account for actual container capacities and held resources, not just row counts. Over-budget execution uses a supported spill path or fails explicitly; never truncate results or swallow corruption errors.

Add database/process-level resource coordination: assign accounting for concurrent queries, caches, transaction-private pages, maintenance and optional code caches without double-counting or omitting shared resources. S1.6 specifies total limits, sub-budget acquisition/release, ordering of waiting/eviction/spill/failure under pressure, cancellation cleanup and prevention of resource-wait deadlocks. Individually bounded queries must not permit unbounded aggregate memory. Limits govern accounted allocations; report RSS and external-runtime overhead separately.

Implement sorted runs/merge first, then partitionable aggregation/hash operations. List unsupported spilling operators and their errors. Reuse allocation infrastructure, but existing bulk scratch does not prove query spill. Specify durable scratch registration/ownership, release, crash cleanup, disk exhaustion and shared handles.

Distinguish logically read-only transactions from physically read-only files. A logically read-only transaction cannot mutate user graph data; allocating query scratch in a writable file requires an explicit internal permission/lifecycle protocol and cannot bypass the user-mutation prohibition. Physically read-only files cannot hold new scratch. Under strict single-file constraints, fail explicitly when a query exceeds memory and has no supported path. Temporary pages are outside ordinary user-data roots; define separate reachability, active-query pins and safe reclamation identities so unrelated long snapshots do not unnecessarily retain them. Scratch allocation/release and user commits must not lose each other's allocator updates. Crash cleanup may reclaim temporary data, never user data or pages with active owners.

Budget foreground work, reclamation and compaction separately. When long snapshots prevent reuse, expose backlog and apply limits instead of growing indefinitely or reclaiming referenced pages.

### A7: Format evolution and implementation boundaries

Specify each new root/page type/descriptor, codec field/width/endianness, version, reachability, atomic maintenance, retirement and integrity walker. Reuse namespaces/shared allocator and prefixed cross-platform enums. Test explicit old-format rejection. Do not copy version numbers from archives into code.

Record implemented, pending-validation, rejected and replaced decisions. A3/A4 currently establish goals, not finalized codecs. On adoption update both this page and affected storage-specification sections, removing conflicting future-policy restrictions while retaining historical evidence.

Retain the current development policy of rejecting old files after a format change; it is not a permanent compatibility promise. S1.7 must define the trigger for stable-format commitments, envelope/Superblock/local-codec compatibility matrices and rejection of unsupported combinations. Before a stable release, establish migration strategy, original-file protection, capacity requirements, validation and failure recovery. This round delivers that release prerequisite and version boundaries, not an implicit migration-tool implementation or a release date. Deferring migration now must not leave future evolution without explicit ownership.

### 6.3 Admission rules

- Correctness, atomic publication, recovery, snapshots, budgets and cleanup must pass. Only relevant module tests; no full suite or coverage gate. Coverage may assist diagnosis.
- S0 preregisters primary goals, protected workloads and resource limits; do not change success criteria after results. Default expectation: at least 10% P50 improvement in the primary bottleneck case, repeatable across processes; protected P50/P95 must not show a stable regression above 5% and beyond control noise. Borderline/noisy results are inconclusive and need targeted repetition. These are decision thresholds, not universal performance promises.
- Do not increase memory limits. Report process RSS, query memory, read/write bytes and steady-state file size separately. Stable resource growth above 5% requires attribution and an explicit admission decision. A3/A4 must not trade uncontrolled writes/space/point-read regressions for scans. Exceeding protected thresholds requires a concrete tradeoff and user agreement, not silent relaxation.
- Lower CPU/allocation counts with uncertain end-to-end benefit must be reported as such, not claimed as speedups. Reject unhelpful complexity and preserve controls. Correctness fixes are not required to deliver a 10% speedup.
- Classify performance changes versus foundational contract/interface changes in advance. The default 10% target applies to primary performance experiments, not every foundational commit. Admit foundations by explicit dependent capabilities, semantic/lifetime tests, complexity and protected-workload cost, recording which later task validates the benefit. Never relabel a failed performance experiment as infrastructure to evade admission, or accept unnecessary lasting complexity solely because it barely crosses a threshold.
- Kuzu parity or better is the objective on equivalent core workloads/resources, not a promise for all workloads. S6 reports remaining gaps; checklist completion does not automatically establish the performance objective.
