# Core Performance Refactoring Plan

Updated: 2026-10-22. Plan ID: `core-cost-20261022`. **This is the sole active optimization checklist. Implementation progress is 25%; P1 is accepted and the Kuzu performance objective is unmet.**

Eliminate the work amplification behind order-of-magnitude gaps and meet or exceed Kuzu on core workloads with equivalent semantics, durability, and resources. Code, tests, or archives do not substitute for that objective. Previous tasks, completed items, chronological logs, and percentages have been removed from this plan. Existing capabilities, failure evidence, and format contracts remain valid and must not be deleted with the old checklist.

## 1. Scope and invariants

Implement only three connected paths: **incremental metadata commit, directly typed scans, and bulk import reusing those mechanisms**. Memory views support the first two; they are not a separate general caching project.

- Preserve the general property graph, dynamic properties, multiple labels, stable logical IDs, and existing Cypher, transaction, QueryBuilder, GDS, Vector, Driver ABI, and binding semantics. Vector dimension expansion is out of scope.
- Retain strict single-file storage, COW, A/B Superblock, data-before-root, and durable acknowledgement. Do not obtain speedups by disabling synchronization, weakening validation, adding threads, or using unlimited caches. WAL, group commit, LSM, JIT, and wholesale backend replacement are out of scope.
- Preserve snapshots, read-your-writes, old pins, relocation, safe reclamation, cancellation, and unified resource accounting. Retain existing sort and DISTINCT/UNION spill; operators without spill must fail within explicit bounds.
- Never overwrite published physical pages. Keep logical IDs, physical locations, generations, and snapshot identities distinct. Specify any format change in the [storage specification](native-single-file-storage-plan) first, including versioning and old-file rejection/migration; never overwrite user files.
- Preserve macOS/Linux/Windows portability and the WASM path; list actually tested platforms. Independent platform release gates belong to [release follow-ups](native-remaining-work-roadmap); Linux results do not establish three-platform acceptance.
- Run only necessary affected-module unit tests, not the full suite. `--file` is not a test filter: use named suite/test filters. Documentation-only changes require documentation checks only.

## 2. Known problems and evidence limits

| Problem | Existing evidence | Work to eliminate |
|---|---|---|
| Metadata amplification on small writes | One SET diagnostic counted 6,698 metadata-page reads, 3 complete route collections, and 2 frame-count calculations | Complete route collection, complete-set construction, and repeated capacity planning during ordinary commits |
| Copies despite memory hits | Read diagnostics counted about 95,000 metadata-cache hits and about 139 MB of fixed-object copies | Repeated copies of decoded pages and per-value acquisition of shared state |
| Scan scope and representation | Country filter/grouping examined 225,000 nodes and decoded 100,000 property values | Unrelated entity visits and generic-value to typed-batch to row-object conversions |
| Confounded write measurements | Preflushing the copied database changed traced SET latency from about 168 ms to 79–102 ms | Charging dirty database-copy pages to transaction synchronization |

These are limited diagnostics, not new formal scores. Metadata-page counters are not disk I/O; fixed-copy counters sum `sizeof(Page)`, not measured memory traffic. Timers overlap, and the scan timer includes consumer callbacks. Exclusive read-side CPU shares remain unmeasured; do not attribute all time to directories. Reducing enumeration from 225,000 to 100,000 alone cannot explain or eliminate an approximately 50-fold aggregation gap.

Source anchors: `nextBootstrapFrameCount` and `publishNextBootstrap` in `MetadataPageRouteDirectory.cpp`; `prepareBatchPublication` in `RelocatableMetadataStore.cpp`; `find`/`findView` in `MetadataPageReadContext.hpp`; node scans in `EntityPageStore.cpp`; and the generic-value batch input in `BoundNodeScanBatch.hpp`. Recheck frozen source rather than relying on line numbers.

Previous formal results are in repository directory `benchmarks/architecture-design/decisions/20261022-r7-final-admission/`, with delivery evidence in `20261022-r7-bounded-repair/`. These are historical controls, not the corrected baseline. P0 must preserve diagnostic source, actual engine SHA, commands, and raw output; session-local paths are not delivery evidence.

## 3. Sequence, progress, and scope control

Execute **P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7**. P1/P2 together implement incremental commit; P3/P4/P5 together implement the read-path change. Finishing one component does not resolve the whole problem.

|---|---|---:|---|
| P0 | Corrected measurement, frozen cost contract and baseline | 0% | Baseline complete; exclusive read CPU attribution pending |
| P1 | Route updates driven by changed paths | 25% | Accepted |
| P2 | Incremental capacity planning, atomic publication, and local correctness proofs | 15% | Implementing; not accepted |
| P3 | Snapshot-bound immutable metadata views throughout the path | 10% | Not started |
| P4 | Cost-selected label/candidate scans | 15% | Not started |
| P5 | Directly typed batches from storage through filtering/aggregation | 20% | Not started |
| P6 | Bulk import reusing the new commit path | 5% | Not started |
| P7 | Complete lifecycle, formal performance, and Kuzu objective acceptance | 10% | Not started |

Freeze weights after P0. Award an item's weight only after production integration, its mechanism evidence, and necessary tests all pass. Designs, prototypes, cache-hit rates, and lines of code earn no progress. Progress cannot exceed 90% before P7 passes; gap reports, failed candidates, and archives cannot earn the last 10%. Rewriting this document does not increase implementation progress.

Each round reports percentage, eliminated work, necessary tests, remaining gaps, and Kuzu objective status. Under the user's authorization, **commit and push to remote `work` only when progress increases**; otherwise do neither. Inspect the remote and worktree first; do not reset/stash away user changes.

If performance targets remain unmet, continue diagnosis and repair within scope rather than adding unrelated tasks. If evidence requires changing durability or public semantics, present a concrete design revision for discussion, retain incomplete status, and never silently weaken acceptance.

## 4. P0: Freeze measurement and cost contracts

### 4.1 Correct comparison conditions

Freeze actual source, build options, engine/probe SHA, Kuzu version, CPU/storage, threads, memory limits, datasets, and schema/indexes. Use medium (225,000 nodes, 860,000 edges) and independent holdout (163,000 nodes, 772,000 edges). Never select data based on optimized results.

- Complete private-copy creation and file synchronization before timing. Align preparation across engines and distinguish warm caches, reopen, and genuinely cold caches; reopening alone is not cold-cache testing.
- Queries must return equivalent values, multiplicities, NULLs, and row counts. Writes must have equivalent operations and transaction boundaries and include durable acknowledgement. Report operation, commit, and end-to-end boundaries rather than selecting the shortest measurement.
- Report both production bulk import and an equal-commit-boundary control. Include parsing, data/index construction, commits, and agreed final durability. Different COPY and transaction boundaries do not measure equivalent underlying storage work.
- Record unsupported cases as N/A; retain timeouts, resource rejection, and errors. A core workload without an equivalent measurement remains unaccepted; do not remove it or substitute an easy winner.

### 4.2 Attribute costs before changing structure

Use bounded profiling on one representative path per class: ordinary country filter/real grouping, single-property SET, and bulk import. Separate user CPU, kernel CPU, and waiting; measure route visits/construction, decoding, allocation/copying, computation, page writes, and synchronization. Use sampling or exclusive phase timing; never add nested timers. Explain tracing overhead against an untraced control and exclude diagnostic latency from formal scores.

Record `M` (total routes), `k` (changed routes), tree height, unique and repeated page accesses, actual COW pages, metadata bytes, synchronization counts, and peak memory. Reads also record candidates, actual entities/fields, batches, and intermediate objects. Check fixed `k` at small, medium, and large metadata sizes, including height changes and split boundaries; this is a mechanism check, not another full benchmark matrix.

P0 produces named cost budgets, equivalent query/write contracts, correctness oracles, and one corrected baseline. Freeze these six primary workloads: ordinary label filter, actual grouping, multi-key grouping, single-property SET, 1,000-edge batch, and full import. Guard against regressions with point lookup, full entities, adjacency, no-op, deletion, and sparse/large properties.

## 5. P1/P2: Small changes must touch changed paths

### 5.1 Incremental tree algorithm

Use the current persistent radix tree for changed-path COW updates, and redesign capacity planning and publication validation together to eliminate complete route traversal from ordinary commits. Radix trees support incremental updates and path copying in theory; their feasibility is not an open question for this plan. Replacing the tree with a B+Tree is not a required task. Only if evidence after incremental refactoring identifies sparse space usage, path depth, or page-write amplification as a remaining dominant radix cost should a comparison of alternative structures be proposed through section 3; this does not automatically expand the current scope. Build a transaction-local change set sorted/deduplicated by logical ID, defining insert, replace, delete, and no-op semantics. Coalesce repeated modifications to their final values.

Construct one COW modification plan for affected leaves and ancestors. Copy shared ancestors once and retain old references for unchanged subtrees. Ordinary commit must not collect complete routes or construct a complete `std::map`/vector; replacing the container with a hash table is insufficient. Retain logical root IDs with physical references during construction instead of reverse-searching a complete route set.

Route work should primarily follow `k` and tree height, approximately `O(k × h)`, rather than `O(M)`; separately account for splits, merges, and allocation. Initial creation, explicit migration, and integrity checks may traverse globally but must be separate from ordinary commit. Do not move work to reads through unbounded delta chains.

### 5.2 Capacity planning and allocation closure

Capacity estimation and publication must consume the same validated modification plan, covering changed data pages, tree paths, split bounds, Catalog, Allocator, routes, retirement, and bootstrap. Validated occupancy/subtree summaries may be maintained; caching a count while rescanning everything is not sufficient.

Resolve the dependency where allocating metadata requires more metadata updates: reserve bounded capacity from changed paths, prepare within it, and process only newly introduced dependencies when extra capacity is needed. Freeze convergence bounds and out-of-space behavior. Repeated whole-tree recalculation is not incremental merely because its retry count is bounded. Charge and refund over-reservation; unpublished candidates must not leak ID/page ownership.

### 5.3 Correctness and lifecycle

Reuse published immutable subtrees through exact provenance, generation, and pins. Validate key ranges, directory types, owners, child references, aliases/duplicates, and allocation ownership on new paths. Enumerate every invariant previously established by global checks, supplying a local proof or required auxiliary index. Use the local-access validation plus full-integrity contract confirmed by the user on 2026-10-22: ordinary commits validate accessed pages and new paths, reusing untouched subtrees by exact immutable references. Fresh corruption in unvisited branches is detected on first access or explicit complete integrity. Complete checks still validate global duplicates, aliases, and orphans; new changes must not introduce them. Access validation, atomic publication, and durability are not weakened.

Keep data/metadata durability before A/B publication and acknowledgement. Cover same-page changes, cross-leaf split/merge, last-entry deletion, sparse IDs, old snapshots, conflicts, cancellation, budget/space exhaustion, write/sync failure, reopen, retirement, relocation, and reuse. Do not fix routes while leaving another ordinary-commit global traversal in Allocator, Catalog, or retirement.

Acceptance: increasing `M` at fixed `k` must not cause complete-set materialization or routine global traversal; repeated accesses and page writes must meet registered budgets. Establish mechanisms first; P7 verifies formal end-to-end gains.

## 6. P3: Memory structures must eliminate work

Prefer existing immutable `findView` paths and audit hot `find` copies. Hold shared page views once per query/batch instead of per-value locking, LRU mutation, acquisition, or validation. Writers modify private COW images only; copy escaping results as needed before pins are released and transfer resource ownership.

Page/route cache keys must bind database, logical/physical identity, generation, snapshot root, and applicable I/O epoch. Never let old snapshots hit new locations or copy a complete global map per commit. If needed, compare demand-loaded segmented arrays/radix mappings. Do not require the whole database in RAM or introduce a second authoritative table duplicating existing caches.

Acceptance: materially reduce fixed-object copies and move reuse to batch/page granularity. Remain correct and bounded under low memory, eviction, reopen, and long-lived pins. Report residency, initial construction, and rebuild cost; do not hide whole-database preload during startup.

## 7. P4/P5: Directly typed scan execution

### 7.1 Candidate scope and access choice

Audit and reuse existing label/property indexes and statistics before adding structures. Compare sorted IDs/block bitmaps with sequential scans for sparse candidates. Choose by selectivity, column width, and locality; do not force random gathers for high-coverage labels. Page grouping must preserve required ordinals, duplicates, and output order.

Keep multi-label intersections, deletion, transaction overlays, and old snapshots consistent. Maintain derived label structures atomically or define snapshot validity explicitly. Do not gain speed by skipping label authentication. P4 addresses candidate scope only; it does not by itself establish an order-of-magnitude scan improvement.

### 7.2 Direct batch representation and consumers

Define one contract for typed scalar buffers, NULL/missing states, string dictionaries or offsets, selection vectors, entity references, ownership, and budgets. Producers directly fill or borrow appropriate typed columns. Ordinary filtering/projection/aggregation must not first construct a complete `PropertyValue` matrix for conversion or fall back wholesale to per-row property maps afterward.

First connect ordinary scan → filter/project → actual single/multi-key group-by → owning output. Low-cardinality strings may use dictionary codes and counters; codes from different dictionaries are not directly comparable without unification or logical-value comparison. Preserve numeric types, overflow, NaN, NULL, missing values, multiplicity, and complete tuple equality. Materialize full entities only where required.

Reuse batch identity, resource accounting, and spill. Batch admission charges actual capacity; wide rows shrink batches. Complex consumers may retain named adapters with triggers and costs, but primary workloads must not rely on them. Random point/neighbor reads must not scan entire column groups.

### 7.3 Decide whether persistent layout must change

Separate fetching, conversion, and computation first. If ROW positioning/decoding still dominates, compare compact field blocks with ROW under the same executor; adding caches alone is not completion. Demonstrate a bounded prototype benefit before full lifecycle work. The existing hybrid layout is not presumed successful.

Define ownership for dense, sparse/mixed-type, and large fields without complete duplicate data. Field blocks need direct owner/ordinal mapping, presence/type state, and selective-read boundaries. An update must not unconditionally rewrite a large group. Include block size, per-update work bounds, random gather, conversion/demotion, old-version space, deletion, reclamation, and file growth. New formats follow section 1.

Acceptance: primary workloads must actually reduce positioning, generic objects, and repeated decoding. Cover empty input, type changes, multiple labels/keys, full entities, and low budgets. A column prototype without production consumers or update lifecycle earns no P5 progress.

## 8. P6: Bulk import reusing the new mechanisms

Confirm dominant import costs in P0. Reuse incremental commit and existing bulk APIs, merge entity/property changes by page, and build indexes from sorted batches where appropriate instead of per-row lookup/update and repeated publication. Do not create an import backend inconsistent with online storage.

Register memory limits, batch size, transaction boundaries, scratch usage, failure visibility, recovery, and cleanup. Include all indexes, constraints, and final durability. Over-memory input must use existing supported bounded mechanisms or fail explicitly; do not expand this into a general external-sort rewrite. Verify query results, node/edge counts, and index validity after import.

## 9. P7: Material gains and final objective

### 9.1 Measurement windows and acceptance

Run the complete matrix once for the corrected P0 baseline and once after final P7 freeze. During implementation prefer counters and module tests; allow one bounded prototype diagnostic per core route when deciding whether to invest in its complete lifecycle. Add targeted measurements only for new failures or contradictory evidence; never rerun the matrix after every commit.

Use at least 3 independent processes with 3 warmups and 10 measurements per query process. Import once per process, with at least 3 independent imports. Preserve per-process and pooled P50/P95, every sample, correctness, CPU, I/O, memory, and file growth. The maximum of 3 imports is not a reliable tail percentile. Write counts follow the frozen contract; preparation and verification have explicit excluded boundaries.

**Structural improvement gate:** on both datasets, single-property SET, ordinary label filtering, and actual single-key grouping must each achieve at least 5-fold P50 speedup over the corrected ZYX baseline. This is a target to validate, not a promise or existing result. Small gains require further dominant-cost investigation; counters cannot substitute for latency.

**Kuzu objective gate:** on both datasets, all six frozen core workloads must have final ZYX P50 no higher than the equivalent Kuzu control; reliably estimated query/write P95 must also be no higher. Equality means parity, not superiority; superiority requires consistently lower results across independent processes. Judge import using the equal-transaction control while also displaying production COPY results. Missing, failing, or slower core cases leave the objective unmet and P7 incomplete.

Guard workloads should not regress by more than 5% in P50/P95 against the corrected baseline. Investigate excesses with targeted confirmation; fix stable regressions. Use all preregistered processes, retain slow samples, and never use cross-process extreme envelopes or average speedups to hide individual failures. Increasing resource limits is not acceptance.

### 9.2 Lifecycle and final evidence

Affected modules must cover old pins and post-release reclamation, reopen, fault injection, allocation failure, cancellation, corruption, indexes/constraints, overlays, and cross-path equivalence. Measure space with long-lived snapshots and after they drain; a short plateau is not indefinite steady state. Mechanism tests verify scaling and actual work, not merely mirror implementation.

Preserve source/library identity, commands, input SHA, mechanism counters, necessary tests, raw samples, failures, and limitations in a new directory under `benchmarks/architecture-design/decisions/`. Do not commit large databases or build products; provide reproducible input generation and execution. Formal evidence must not exist only in ignored output or temporary `/workspace` paths.

P7 synchronizes actual changes into the [storage specification](native-single-file-storage-plan) and [capability matrix](native-capability-acceptance-matrix), and publishes per-workload before/after/Kuzu tables. **Mark this plan 100% only when mechanisms, correctness, structural gains, the Kuzu objective, and regression guards all pass.** Otherwise retain incomplete status and identify the next evidenced core cost; reporting the gap is not completion.
