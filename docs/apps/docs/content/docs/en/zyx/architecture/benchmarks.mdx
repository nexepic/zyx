# Benchmarks

ZYX ships a standalone benchmark application (`apps/benchmark`) with **51 benchmarks** across 7 categories: insertion, querying, algorithms, vectors, concurrency, transactions, and storage footprint.

## Categories

| Category | Type flag | What it tests | Benchmark count |
|----------|-----------|---------------|-----------------|
| **Insert** | `insert` | Cypher vs. native API write paths (single and batch), across 4 index modes (none / label / property / both) | 16 |
| **Query** | `query` | Property index lookups, label scans, full scans, and optimizer effectiveness (filter pushdown, AND splitting, join filtering) | 7 |
| **Algo** | `algo` | Shortest path via Cypher and native API on a 1000-node chain | 2 |
| **Vector** | `vector` | Vector insertion (128d/768d, with/without HNSW index) and ANN top-10 search | 5 |
| **Concurrency** | `concurrency` | Single-thread vs. multi-thread comparison for queries, sorting, batch inserts, PQ training, vector search, and concurrent reads | 12 |
| **Transaction** | `transaction` | Implicit commit vs. explicit transaction vs. explicit batch — inserting 1000 nodes per run | 3 |
| **Storage** | `storage` | On-disk footprint profiling: numeric, short text, long text, mixed properties, graph with indexes, and vector indexes | 6 |

## How to Build and Run

Build the benchmark binary:

```bash
ninja -C buildDir zyx-bench
```

Run all benchmarks:

```bash
./buildDir/apps/benchmark/zyx-bench
```

### CLI Options

| Flag | Description |
|------|-------------|
| `-t, --type <type,...>` | Filter by category (comma-separated). Accepts: `insert`, `query`, `algo`, `vector`, `concurrency`, `storage`, `transaction`, `all` |
| `-b, --bench <id,...>` | Run specific benchmark(s) by exact ID |
| `--list` | Print all categories and benchmark IDs, then exit |
| `--list-types` | Print only the 7 category names, then exit |

Type aliases are accepted: `write`/`writes` for insert, `read`/`reads` for query, `algorithm`/`algorithms` for algo, `vec` for vector, `conc`/`parallel` for concurrency, `footprint` for storage, `txn` for transaction.

### Examples

```bash
# Run only insert benchmarks
./buildDir/apps/benchmark/zyx-bench --type insert

# Run query and vector benchmarks
./buildDir/apps/benchmark/zyx-bench --type query,vector

# Run a specific benchmark by ID
./buildDir/apps/benchmark/zyx-bench --bench query.cypher.property_index

# List all available benchmarks
./buildDir/apps/benchmark/zyx-bench --list
```

## Metrics

Latency/throughput benchmarks report four columns:

| Metric | Description |
|--------|-------------|
| **Ops/Sec** | Throughput (operations per second). Batch benchmarks report per-item throughput. |
| **Avg(us)** | Mean latency per operation in microseconds |
| **P99(us)** | 99th-percentile latency from sorted per-iteration timings |
| **Mem(KB)** | Peak RSS via `getrusage` (macOS/Linux) or `GetProcessMemoryInfo` (Windows) |

Each benchmark also reports a **stage breakdown** (`[Stage avg ms/op]`) showing the average time spent in each query engine stage (parsing, planning, execution, etc.), sorted by cost.

Storage benchmarks report the native database file only: `Nodes | Edges | Props | DB(MB) | Bytes/Node`, and export results to `/tmp/zyx_storage_profile.csv`.

## Current Evidence Boundary

Benchmark output is not a completion percentage. The current working tree has
focused read-optimization checkpoints, but no frozen post-checkpoint benchmark
has been approved as the new-versus-old architecture baseline. Historical
measurements may explain hotspots, yet they must not be presented as current
release performance or as proof that the native design is globally faster or
slower.

A formal comparison must use the same commit, dataset manifest, seed, hardware,
compiler flags, thread contract, warmup, iteration count, open mode, and
diagnostic state for both paths. The release artifact must disable per-event
diagnostic tracing and include structural counters such as root descents,
distinct page pins, selected decodes, complete materializations, materialized
bytes, peak RSS, and file size. A profiled run is an attribution artifact, not a
latency baseline. Benchmark-specific branches, query-text exceptions, or
threshold changes are not valid optimization evidence.

The next benchmark run is intentionally deferred until the functional Stage 2-8
consumer migration and its necessary tests are stable. Until then, use focused
GoogleTest results to validate behavior and use benchmark runs only to diagnose
the shared framework; do not use them to close a roadmap stage.

### Current interpretation correction (2026-09-24)

The recent observation that the new path did not improve end-to-end latency does
not mean that the target architecture was fully implemented and lost to the old
one. The current result is explained by incomplete consumer migration: several
workloads still repeat generic Entity/Property routing, and diagnostic event
collection can dominate short runs. The historical focused `306/306` and `77/77`,
pre-Vector-change direct-edge `78/78`, `15/15`, and
current projection `14/14` results are correctness checkpoints, not performance
measurements. Until a no-diagnostic, frozen-manifest comparison is produced, the
only supported conclusion is that the optimization roadmap remains partial.

The current working tree also contains an unverified lazy-`EntityRef` Vector
procedure implementation. It is intended to validate and filter hits before
complete Node materialization, keep selected and complete Property caches
separate, and batch-read only surviving final Node outputs. The last Vector
`8/8` and logical-backend `57/57` records predate this change and must not be
reported as current evidence until the target is rebuilt and rerun.

|------------|---------------|

| `insert.native.batch.<mode>` | `db.createNodes()` with pre-allocated data |

### Query Benchmarks

Setup: 500 User nodes + 2000 noise nodes (Product/Order/Category/Log).

| ID | What it tests |
|----|---------------|

### Concurrency Benchmarks

Each scenario has a `single_thread` and `multi_thread` variant (using `hardware_concurrency()` threads). Data size: 10000 nodes, 5 iterations.

| ID Pair | What it tests |
|---------|---------------|

## Interpreting Results

1. **Fix your hardware and compiler flags** — Results vary significantly across CPUs, storage devices, and optimization levels. Always use the same `-O3` release build for comparisons.
2. **Separate cold-start from steady-state** — The first run exercises file open/recovery and page-cache admission; subsequent runs benefit from warm caches. The current single-file native format has no production sidecar WAL, so do not attribute cold-start cost to WAL creation. Report both.
3. **Use `PROFILE` and `EXPLAIN`** — Combine benchmark numbers with query plan analysis to understand *why* a query is fast or slow.
4. **Check index hit rates** — A query may appear slow not because of the engine, but because an expected index is missing.
5. **Compare across versions with identical setup** — Same compiler, same data distribution, same hardware. Anything else introduces confounding variables.

## Optimization Verification Matrix (2026-09-20)

The graph-comparison executable is the scale and cross-database harness for the optimization
roadmap. Unlike `zyx-bench`, it consumes a frozen generated dataset and emits one JSON event per
sample. A single workload can be isolated without changing its implementation:

```bash
./buildRelease/zyx-compare-bench \
  --dataset <dataset-directory> \
  --db-path <temporary-database-file> \
  --scale medium \
  --profile multihop \
  --execution-mode opened \
  --workload varlength_frontier_count \
  --warmup 0 \
  --iterations 1
```

`--workload` must name a workload registered for `--profile`; a mismatch fails argument
validation instead of silently performing only the load phase. Omit `--workload` to run the full
profile. The supported execution modes remain `opened`, `warm`, and `cold-ish`.

The following Release results use seed `42`, `warmup=0`, `iterations=1`, and the same generated
small/medium datasets. They are structural diagnostics, not stable percentile claims.

## Optimization Roadmap

Follow the [architecture and performance plan](optimization): A1–A7, O1–O8 and S0–S6. Completed P0–P7 is historical evidence, not subsequent work. Existing benchmark records require current-source provenance, result, timing and resource verification. Fix comparable control/current/Kuzu binary provenance, data manifests, parameters, consumption and cache modes; report latency percentiles, memory, file size, I/O and structural counters. Never divide cross-environment results. The implementation plan owns admission and regression thresholds.

The current working tree contains an additional generic expression batching
change in `LogicalPlanReadRuntime.cpp` for Filter, Project, Aggregate, and Sort.
It includes complete-Entity prefetch for `properties(entity)`, `keys(entity)`, and
`entity{.*}`. The historical six-suite `306/306` runtime/executor checkpoint
predates the latest complete-Entity correlated-subquery change; the current
direct-edge suite passed `78/78` after that change, but that result predates the
current lazy-`EntityRef` Vector procedure change. The focused evidence includes
the deferred-EntityRef Sort-key and earlier read-only correlated-subquery import
regressions. No benchmark has been
rerun after the change. Therefore, benchmark results recorded before that
checkpoint must not be described as measurements of it. The focused checkpoint
also does not prove that every consumer uses the shared contract: the direct
Filter complete-Entity predicate contract now has focused evidence, while
procedure/GDS/overlay/maintenance paths and the
remaining complex JOIN/OPTIONAL MATCH/UNION payload audit are still open. Until that
consumer audit is complete, a lack of end-to-end speedup is an implementation
status signal, not evidence that the native storage design should be replaced by
a benchmark-specific path.

The current working tree also adds a shape-aware resumable Node scan to the
logical read contract and uses it from GDS projection construction. Native
page-backed readers can now omit labels and Property roots that the projection
does not request; generic adapters retain the complete-scan fallback. The
`zyx_test_suite` target compiles and links this checkpoint, and the focused
projection/adapter shape-equivalence run passes 15/15 tests. No benchmark has
been rerun after it, so results recorded above must not be attributed to this
scan change.

Separately, the native `algo.shortestPath` procedure has a `ShortestPath*`
focused boundary group at `3/3` for bounded final path-Node materialization.
The native `gds.shortestPath.dijkstra.stream` path uses the same sorted batch
helper and restores logical path order after storage-order reads. The Vector
procedure checkpoint passes `8/8` for score-order restoration without a
duplicate ID-keyed Node map. These are correctness/memory checkpoints, not
benchmark measurements and not part of the six-suite `306/306` count;
procedure Property-expression batching, GDS, overlay, maintenance, and
full-regression consumers remain open.

## Regression Baseline Contract

When using the graph-comparison runner's `--baseline-summary` p50 regression gate, pass the `summary.csv` from an
earlier runner result. The runner reads its sibling `environment.json` and compares the dataset manifest, database set,
scale/seed, profile, execution mode, warmup/iterations, thread contract, and platform field by field. A missing,
non-object JSON, or any mismatch fails `baseline_environment_provenance`; Git commit is intentionally excluded because
the purpose is to compare revisions under one frozen configuration.

This proves only that the historical and current runs are comparable, not that production performance is approved. A
release gate still records target hardware, frozen production-scale input, reviewed thresholds, Vector
exactness/Recall/QPS/build/update/recovery results, and macOS/Linux/Windows acceptance evidence.
