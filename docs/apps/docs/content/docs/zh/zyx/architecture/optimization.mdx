# 核心性能重构实施方案

更新：2026-10-22。计划标识：`core-cost-20261022`。**本页是唯一有效的优化实施清单。当前实施进度 50%；P1/P2/P3 已验收，Kuzu 性能目标未达成。**

目标是消除数量级差距背后的工作放大，使核心场景在相同语义、持久化和资源条件下达到或超过 Kuzu。完成代码、测试或归档不能代替性能目标。旧任务、已完成项、过程日志和旧百分比已清理；它们不再驱动实施。现有能力、失败证据和格式契约继续有效，不能因清理文档而删除。

## 1. 聚焦范围与不变量

本轮只推进三条相关路径：**增量元数据提交、直接类型化扫描、复用上述机制的批量导入**。内存视图是前两条的配套机制，不另建通用缓存工程。

- 保留通用属性图、动态属性、多标签、稳定逻辑 ID，以及现有 Cypher、事务、QueryBuilder、GDS、Vector、Driver ABI 和绑定语义。向量扩维不在本轮范围。
- 保留严格单文件、COW、A/B Superblock、data-before-root 与 durable acknowledgement。禁止用关闭同步、降低校验、增加线程数或无限缓存制造提速。本轮不引入 WAL、group commit、LSM、JIT 或整体 backend 重写。
- 保留快照、read-your-writes、旧 pin、页面搬迁、安全回收、取消和统一资源预算。现有 sort、DISTINCT/UNION spill 不得丢失；不支持 spill 的算子须明确有界失败。
- 旧物理页不可原地修改。逻辑 ID、物理位置、generation 和快照身份不能混用。任何文件格式变化先更新[存储规范](native-single-file-storage-plan)，明确版本与旧库拒绝/迁移行为；不覆盖用户文件。
- 保持 macOS/Linux/Windows 可移植及 WASM 路径；实际验证平台单列。跨平台发布门禁归[发布事项](native-remaining-work-roadmap)，不得用 Linux 成绩冒充三平台验收。
- 只执行必要的受影响模块单元测试，不执行全量单测。`--file` 不是测试过滤器，必须使用具体 suite/test 过滤。文档变更只检查文档。

## 2. 已知问题与证据边界

| 问题 | 已有证据 | 本轮要消除的工作 |
|---|---|---|
| 小写入元数据放大 | 单属性 SET 诊断有 6,698 次元数据页读取计数；完整路由收集 3 次、帧数计算 2 次 | 普通提交中的完整路由收集、完整集合构造、重复空间规划 |
| 内存命中仍有复制 | 读取诊断约 9.5 万次元数据缓存命中，固定对象复制计数约 139 MB | 热路径中重复复制完整已解码页、逐值获取共享状态 |
| 扫描范围与表示成本 | country 过滤/分组扫描 225,000 个节点、解码 100,000 个属性值 | 无关实体访问，以及从通用值到类型批再回到行对象的转换 |
| 写入测量混杂 | SET 先同步副本后，带追踪耗时从约 168 ms 变为 79–102 ms | 将准备副本的脏页刷盘计入事务性能 |

这些是少量诊断样本，不是新的正式成绩。元数据页计数不是磁盘 I/O；固定复制计数累加 `sizeof(Page)`，不是实测内存流量；内部 timer 有嵌套，扫描 timer 包含消费者回调。读取侧尚未获得独立 CPU 热点占比，不能把全部时间归因于目录。仅减少 225,000 到 100,000 条枚举，不能解释或消除约 50 倍的聚合差距。

源码锚点：`MetadataPageRouteDirectory.cpp` 的 `nextBootstrapFrameCount`、`publishNextBootstrap`；`RelocatableMetadataStore.cpp` 的 `prepareBatchPublication`；`MetadataPageReadContext.hpp` 的 `find`/`findView`；`EntityPageStore.cpp` 的节点扫描；`BoundNodeScanBatch.hpp` 的通用值批入口。以实际冻结源码复核，不依赖行号。

上一轮正式数据保存在仓库 `benchmarks/architecture-design/decisions/20261022-r7-final-admission/`，交付归档在 `20261022-r7-bounded-repair/`。它们只用于历史对照，不能替代修正后的本轮基线。P0 必须保存诊断源码、实际引擎 SHA、命令和原始输出；会话临时路径不是交付证据。

## 3. 执行顺序、进度与停止扩散规则

按 **P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7** 推进。P1/P2 共同构成增量提交，P3/P4/P5 共同构成读取重构；不得只完成其中一部分就宣称对应问题解决。

| 项目 | 必须交付的结果 | 权重 | 状态 |
|---|---|---:|---|
| P0 | 修正测量、冻结成本合同和基线 | 0% | 基线与读取独立 CPU 归因完成 |
| P1 | 变化路径驱动的路由更新 | 25% | 已验收 |
| P2 | 增量空间规划、原子发布和局部正确性证明 | 15% | 已验收 |
| P3 | 快照内不可变元数据视图贯通 | 10% | 已验收 |
| P4 | 成本选择的标签/候选扫描 | 15% | 未开始 |
| P5 | 存储到过滤/聚合的直接类型化批 | 20% | 未开始 |
| P6 | 复用新提交路径的批量导入 | 5% | 未开始 |
| P7 | 完整生命周期、正式性能与 Kuzu 目标验收 | 10% | 未开始 |

权重在 P0 后冻结。只有生产路径接入、该项机制证据和必要测试全部通过，才能一次性获得其权重；设计、原型、缓存命中率或代码行数不计进度。P7 未通过最多 90%，不得把最终差距报告、失败候选或归档算成剩余 10%。文档重写不增加实施进度。

每轮报告：当前百分比、消除的工作、必要测试、剩余缺口和 Kuzu 目标状态。依用户授权，**仅进度增长时提交并推送远程 `work`**；进度不变不提交、不推送。先检查远程和工作树，不 reset/stash 覆盖用户修改。

性能目标未达到时继续在本范围定位和修复，不另加无关优化凑进度。若证据证明必须改变持久化协议或公开语义，先提交具体设计修订供讨论，保持目标未完成，不能偷偷放宽验收。

## 4. P0：冻结测量与成本合同

### 4.1 修正比较条件

冻结当前实际源码、编译选项、引擎/探针 SHA、Kuzu 版本、CPU/存储、线程、内存预算、数据和 schema/index。主数据沿用 medium（225,000 节点、860,000 边）与独立 holdout（163,000 节点、772,000 边）。不得依据优化后结果选择数据。

- 私有副本在计时前完成文件复制和同步；两引擎准备一致，明确热缓存、重新打开与真正冷缓存的区别。只重新打开不称为冷缓存。
- 查询返回相同值、重复次数、NULL 和行数；写入使用相同操作与事务边界，计时包含 durable acknowledgement。区分纯操作、提交、完整端到端时间，不能只选较短者。
- 导入分别报告“生产批量导入”和“相同提交边界对照”；包含解析、数据/索引构建、提交及约定的最终持久化，不把 Kuzu COPY 与不同事务边界当作严格等价的底层对比。
- 不支持记 N/A；超时、资源拒绝和错误保留。必须比较的核心场景若无法等价测量，保持验收未完成，不删项或换成容易获胜的场景。

### 4.2 先定位再改造

每类只选择一个代表路径做有限剖析：普通 country 过滤/真实分组、单属性 SET、批量导入。区分用户 CPU、内核 CPU、等待；独立统计路由访问/构造、解码、分配/复制、算子计算、写页和同步。使用采样剖析或互斥阶段计时；不可相加嵌套 timer。追踪开销用不带追踪的控制说明，不作为正式延迟。

登记 `M`（总路由数）、`k`（修改路由数）、树高、唯一访问页、重复访问、实际 COW 页、元数据字节、同步次数、内存峰值。读取登记候选数、实际实体/字段数、批数和中间对象数。以小、中、大三个元数据规模固定 `k` 做机制检查，包含树高度变化和分裂边界；不把它变成全矩阵性能测试。

P0 输出具名成本预算、等价查询/写入合同、正确性 oracle 和一次修正后的基线。默认主场景固定为：普通标签过滤、真实分组、多键分组、单属性 SET、1,000 边批写、全量导入。补充点查、完整实体、邻接、no-op、删除、稀疏/大字段作为回归守护。

## 5. P1/P2：让小修改只处理变化路径

### 5.1 增量树算法

采用现有持久 radix tree，实现变化路径驱动的 COW 更新，并同步重构空间规划和发布校验，消除普通提交中的全量路由遍历。radix tree 在理论上支持增量更新与路径复制，本轮不再将其列为待验证的可行性问题。B+Tree 替换不属于当前必做项；只有完成增量改造后，仍有证据表明 radix 的稀疏空间占用、路径深度或页面写放大构成主要瓶颈，才按第 3 节流程提出替代结构比较，不自动扩展本轮范围。先形成按逻辑 ID 排序/去重的事务变化集合，定义新增、替换、删除和无变化语义。同批多次修改合并为最终值。

按受影响叶子与祖先构造一次 COW 修改计划；共享祖先只复制一次，未变化子树直接复用旧引用。普通提交不得调用完整路由收集或构造完整 `std::map`/vector；把容器换成哈希表不算解决。逻辑根 ID 与物理引用在构造时成对保留，不从完整集合反向寻找根。

目标：路由算法的访问量主要由 `k` 和树高决定，近似 `O(k × h)`，而非 `O(M)`；分裂、合并和分配成本单列。首次建库、显式迁移与完整性检查可以全量，但必须与普通提交分离。批处理不能通过无限 delta 链把工作推迟到读侧。

### 5.2 空间规划与分配闭环

空间估算和发布共用同一份已验证修改计划，包含变化数据页、树路径、分裂上界、Catalog、Allocator、路由、退役和 bootstrap。可维护可验证的节点占用/子树统计，但不能缓存一次全量计数后每次仍重新扫描。

明确元数据页分配又产生元数据修改的闭环：先根据变化路径预留有界容量，再在该容量内准备，必要补充仅处理新增依赖；冻结收敛上界与空间不足错误。不能依赖最多若干次“全树重算”伪装增量。过度预留必须计费并退款，候选未发布不得泄露 ID/页所有权。

### 5.3 正确性与生命周期

已发布不可变子树通过精确来源身份、generation 和 pin 复用；新路径校验键范围、目录类型、owner、子引用、别名/重复以及分配所有权。列出原全局检查保证的每个不变量，逐项说明增量证明或必要辅助索引；采用用户于 2026-10-22 确认的“局部访问校验＋完整 integrity”合同：普通提交验证实际访问页与新路径，未变化子树按精确不可变引用复用；未访问分支中新发生的损坏在首次访问或显式完整 integrity 时发现。完整检查仍验证全局重复、别名和孤立；新修改不能引入这些错误。不得弱化实际访问校验、原子发布或持久化保证。

保持数据与元数据先落盘，再发布 A/B 根，再确认。覆盖同页多修改、跨叶分裂/合并、删除最后项、稀疏 ID、旧快照、并发冲突、取消、预算/空间不足、写入或 sync 失败、重开、退休和搬迁复用。不能只修路由，留下 Allocator/Catalog/retire 的另一条普通提交全量遍历。

验收：固定 `k` 增大 `M` 时，无完整集合物化和常规全局遍历；重复访问及页写量符合登记预算。机制证据先通过，P7 再检验正式端到端收益。

P2 验收：普通提交的所有权准备只验证实际变化池，空闲池链表与容量计数避免扫描满池；变化路径同时产生退休帧记录，按最老快照代际回收。发布后的接收与所有权确认不再申请内存。缺少完整增量证明、显式迁移/回收或恢复时才重建全图证明。3/300/900 个 Catalog 叶、固定单项修改中，路由源帧为 2/4/5，所有权访问均为 6 次，普通全图扫描均为 0；298 项相关模块测试通过。证据：`benchmarks/architecture-design/decisions/20261022-core-cost-ownership/acceptance.json`。这不代表最终性能目标已通过。

## 6. P3：内存结构必须消除工作

优先贯通已有 `findView` 等不可变视图，审计热路径 `find` 的复制；查询/批次持有一次共享页视图，避免逐值锁、LRU 更新、引用获取和重复校验。写者只修改私有 COW 图像，输出逃逸或释放 pin 前按需复制并转移预算。

页/路由缓存键必须绑定数据库、逻辑/物理身份、generation、快照根及适用的 I/O epoch。不得让旧快照命中新位置，也不得每提交复制整份全局映射。必要时比较按需分段数组/radix 映射；不要求全库常驻内存，不新增与既有缓存重叠的第二套权威表。

验收：热读取的固定对象复制明显下降，工作转为批/页级复用；低内存、缓存淘汰、重开和长寿命 pin 下仍正确有界。内存驻留、首次构建及重建成本全部报告，不把启动时全量预加载藏出统计。

P3 验收：热查找贯通不可变 bootstrap/radix/Catalog/Allocator 视图和单子路径解析；保留现有缓存上限、预算、快照与 I/O epoch 校验。medium 过滤/真实分组的固定对象复制计数下降 99.34%，460 项相关模块测试通过；此为机制计数，非时延或 Kuzu 验收。证据：`benchmarks/architecture-design/decisions/20261022-core-cost-views/`。读取独立 CPU 采样及局限见 `20261022-core-cost-read-cpu/`；当前热读以用户 CPU 为主。

## 7. P4/P5：贯通直接类型化扫描

### 7.1 候选范围与访问选择

审计已有标签/属性索引及统计，先复用，避免重复建设。对稀疏候选比较排序 ID/分块位图与顺序扫描；根据选择率、列宽和页局部性选择路径，高覆盖标签不强制随机 gather。候选按页分组时保留必要 ordinal、重复及结果顺序。

多标签交集、删除、事务 overlay 与旧快照必须一致。派生标签结构需与主数据原子维护或有明确快照有效性。不能以跳过标签认证换提速。P4 只解决候选范围，不能将其宣称为全部扫描数量级收益。

### 7.2 直接批表示与消费

定义同一批合同：类型化标量缓冲区、NULL/缺失状态、字符串字典或 offsets、选择向量、实体引用、所有权和预算。生产者直接填充或借用适用类型列；常规过滤/投影/聚合不能先构造完整 `PropertyValue` 矩阵再转换，也不能随后整体回到逐行属性 map。

先贯通普通 scan → filter/project → 真正单/多键 group-by → owning output。低基数字符串可做字典编码及编码计数；跨块字典 ID 不得直接相等，须统一或比较逻辑值。保持数值类型、溢出、NaN、NULL、缺失、重复及完整 tuple 比较。只在返回完整实体或必要输出时物化。

复用现有批身份、资源账户和 spill。批量计费覆盖真实容量；宽行缩批。复杂消费者可保留具名适配器，注明触发条件和成本，不能让主场景依赖该回退。随机点查/邻接不能被强迫扫描整列组。

### 7.3 是否需要持久布局改变

先将取值、转换、计算成本分离。若 ROW 定位/解码仍主导，必须比较紧凑字段块与同执行器 ROW 对照，不靠叠加缓存宣告完成。小范围原型先证明收益，再做生命周期；既有混合布局不是默认成功方案。

稠密字段、稀疏/混合类型、大值需要明确归属，避免完整双份数据。字段块应有直接 owner/ordinal 映射、presence/type 与选读边界；更新不得无条件重写整个大组。块大小、单次修改上限、随机 gather、转换/降级、旧版本空间、删除、回收和文件增长全部纳入成本。新格式遵循第 1 节。

验收：主场景实际减少定位、通用对象构造和重复解码；正确性覆盖空输入、类型变化、多标签、多键、完整实体及低预算。缺少生产消费链路或更新生命周期的列原型不得计入 P5。

## 8. P6：复用新机制的批量导入

先用 P0 导入剖析确认主要成本。复用增量提交与已有批写接口，按页合并实体/属性写入；适用时排序后批量构建索引，避免每行独立查改和重复发布。禁止为导入再建一个与在线存储不一致的 backend。

登记内存上限、批大小、提交边界、临时空间、失败后可见状态、恢复与清理。计入所有索引、约束检查和最终持久化，不以省略能力换吞吐。超内存输入必须使用现有可支持的有界机制或明确拒绝；不扩展成通用外排重写。导入完成后的查询结果、节点/边数和索引有效性必须验证。

## 9. P7：实质收益与最终目标

### 9.1 性能窗口与准入

完整性能矩阵只在 P0 修正基线和 P7 最终冻结后各跑一次。实现期间优先机制计数和模块测试；每条核心路线仅在决定是否投入完整生命周期时安排一次小范围原型诊断。新失败或证据矛盾才追加针对性测量，禁止每个提交重跑全矩阵。

最终采用至少 3 个独立进程，每个查询进程 3 次预热、10 次测量；导入每进程一次，至少 3 次独立导入。每进程与合并 P50/P95、全部样本、正确性、CPU、I/O、内存和文件增长均保留。导入 3 个样本的最大值不能解释为可靠尾分位。写入次数按冻结合同，预处理与核验均在明确边界外。

**结构性收益门槛**：在两个数据集上，单属性 SET、普通标签过滤、真实单键分组各自 P50 相对修正后的 ZYX 基线至少提速 5 倍；这个门槛是待验证目标，不是承诺或既有成绩。若仅小幅收益，继续分析剩余主成本，不能以工作量指标替代时延结果。

**Kuzu 目标门槛**：P0 固定的六个核心场景在两个数据集上，最终 ZYX P50 均不高于等价 Kuzu 对照；可可靠估计的查询/写入 P95 也不高于对照。相等仅可称达到，不可称超越；要称“超过”，须在独立进程重复中稳定更低。导入按等价事务对照判定，生产 COPY 对照同时展示。任一核心项缺测、失败或仍落后，则目标未达成、P7 未完成。

回归守护场景相对修正基线 P50/P95 增幅应不超过 5%。超限要解释噪声并做针对性确认；稳定退化必须修复。使用全部预登记进程，不删慢样本，不使用跨进程极值包络掩盖退化，不用平均提速掩盖单项失败。资源不得靠提高限额通过。

### 9.2 生命周期与最终交付

受影响模块覆盖旧 pin 与释放后回收、重开、故障注入、分配失败、取消、损坏、索引/约束、overlay 和跨路径等价。长寿命快照与排空后的空间分别测量，不能把短平台期当无限稳态。必要机制测试验证规模增长与实际工作量，不写仅镜像实现的测试。

每项证据保存在 `benchmarks/architecture-design/decisions/` 的本轮目录：源码/库身份、命令、输入 SHA、机制计数、必要测试、原始样本、失败与限制。大数据库和构建产物不提交；输入生成与运行方式必须可复现。正式证据不能只存在于忽略目录或 `/workspace` 临时路径。

P7 同步[存储规范](native-single-file-storage-plan)与[能力矩阵](native-capability-acceptance-matrix)中的实际变更，输出逐场景优化前/后/Kuzu 表。**只有机制、正确性、结构性收益、Kuzu 目标和回归守护全部通过，才可将本计划标为 100%。** 目标不满足时保留未完成状态及下一处已证实的核心成本，不将“已报告差距”改称完成。
