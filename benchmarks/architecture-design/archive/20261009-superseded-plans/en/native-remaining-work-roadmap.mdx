## Current Functional Scope

- Preserve all graph capabilities, including Cypher, GDS, Leiden, Vector,
  Driver ABI, and language bindings. Optimization must not remove public behavior.
- Keep the single-file native format and its fail-closed corruption, recovery,
  relocation, snapshot, and reclamation contracts. Do not restore the retired
  Segment-chain or legacy physical-executor implementation for compatibility.
- Finish the consumer audit for Stages 2-8. Existing reusable APIs are
  foundations, not proof that every query, procedure, GDS, overlay, index
  verification, maintenance, or write-batch consumer uses them.
- The current procedure checkpoint is deliberately narrow: native
  `algo.shortestPath` and `gds.shortestPath.dijkstra.stream` batch final
  path-Node materialization through the logical snapshot, while adapters
  without an existence probe retain the explicit complete-read fallback. The
  shared helper restores logical path order after sorted storage reads and
  accounts for duplicate path positions under the materialized-byte bound. This
  does not close the remaining procedure Property-expression, GDS, overlay,
  maintenance, or lifecycle audit. The last verified `ShortestPath*` boundary
  is `3/3`; the existing GDS procedure contract suite covers Dijkstra behavior.
  The previous Vector procedure boundary was `8/8` before the current lazy-
  `EntityRef` change and must be rerun.
- The current GDS projection checkpoint is deliberately narrow as well:
  `LogicalGraphProjection::build()` requests a shape-aware resumable Node scan
  that reads identity and labels only when a label filter is present. Native
  page-backed adapters honor selected-column and complete-property shapes; the
  generic fallback keeps complete-scan semantics. Its earlier focused
  projection/adapter run passes 15/15 tests, while the current projection suite
  passes 14/14 after one-pass staging. Neither result closes the GDS capability
  row or Stage 2/3 because broader consumer, scale, and lifecycle gates remain.
- The current `LogicalPlanReadRuntime.cpp` change introduces
  `selectBatchableExpressions(...)` for Filter, Project, Aggregate, and Sort. It
  is compiled and covered by the focused checkpoint; the remaining work is to
  audit the other Stage 6 consumers and preserve the complete-expression fallback.
  The direct Filter contract (rejected rows, duplicate rows, `NULL`, and
  visitor early-stop) now has focused evidence; the remaining open work is the
  other complete-Entity consumers and lifecycle coverage. The native
  `algo.shortestPath` procedure and `gds.shortestPath.dijkstra.stream` now share
  bounded final path-Node materialization through `readNodesShapedSorted(...)`;
  the helper restores logical path order after sorted storage reads and counts
  duplicate path positions under the byte bound. The last verified
  `ShortestPath*` boundary is `3/3`; the previous Vector procedure boundary was
  `8/8` before the current lazy-`EntityRef` change, and the existing GDS procedure
  contract suite covers Dijkstra behavior; procedure Property-expression
  batching and other procedure paths remain open.
- The current Vector procedure implementation is a pending lazy-`EntityRef`
  checkpoint: validation, filtering, projection, `SKIP`, and `LIMIT` operate on
  references; selected and complete Property caches are distinct; complete Node
  reads happen only for surviving final Node outputs; sorted bounded reads are
  scattered back to score order and repeated references reuse one payload.
  Scalar-only and Property-only outputs should avoid complete Node reads. The
  previous `VectorProcedure*` `8/8` result predates this change and must be rerun
  after compilation; cross-row Property-expression batching for procedures
  remains open.

### Progress authority correction (2026-09-24)

The repository intentionally reports three different states:

1. **Native correctness core**: the native storage owner and minimum focused
   correctness evidence exist. This can be described as a completed functional
   work package even while release gates remain open.
2. **Capability acceptance**: the public contract still needs its lifecycle,
   recovery, resource, binding, performance, coverage, or platform evidence.
   The acceptance matrix may therefore keep a row `IN_PROGRESS` after the
   corresponding native core exists.
3. **Production-read optimization**: logical-plan, procedure, GDS, overlay,
   maintenance, and index-verification consumers have adopted the shared shape
   and bounded-batch contract. This is the separate approximately 34% ledger.

These states are not additive and must not be converted into one percentage.
The current working tree also contains uncommitted runtime changes: focused
results above are valid only for the commands and source revisions named in the
snapshot, while the most recent unfiltered quick run remains historical. A
stage or capability must not be marked complete merely because a focused test
count increased.

## Priority Order

1. Complete the current macOS functional optimization batch and its focused
   correctness tests. The direct Filter complete-Entity predicate contract has
   focused evidence, grouped Aggregate has a focused complete-Entity regression,
   deferred-EntityRef Sort has a focused regression, and read-only correlated
   subquery imports have a focused regression; next cover the remaining complex
   JOIN/OPTIONAL MATCH/UNION payloads. Cover both the safe
   selected-expression subset and the complete-entity/path fallback, including
   ordering, duplicates, `NULL`, byte bounds, cancellation, and strict early-stop.
   The GDS projection shape-aware scan now has an independent 15/15
   projection/adapter regression and a current 14/14 projection-suite result;
   keep its broader consumer, scale, and lifecycle gates separate from those
   focused test results. The last verified ShortestPath 3/3 and pre-change Vector
   procedure 8/8 checkpoints are likewise bounded consumer evidence; the Vector
   change must be rebuilt and rerun, and procedure Property-expression batching
   remains open.
2. Continue the Stage 6 consumer audit, then close the remaining Stage 2-8
   lifecycle, structural-counter, and error-path evidence without adding
   benchmark-specific branches.
3. Keep necessary unit tests with each behavior change. Do not block functional
   migration on a global coverage sprint; comprehensive line, branch, function,
   and region coverage belongs after the final source set is stable.
4. Run a current unfiltered macOS quick suite after a coherent batch of runtime
   changes. Treat older full-suite, coverage, and benchmark artifacts as history.
5. Only after functional migration and legacy cleanup are stable, run the frozen
   no-diagnostic Release benchmark, scale matrix, three-platform validation,
   sanitizer checks, binding checks, and final coverage gates.

## Evidence Rules

- A focused test count is evidence only for the compiled worktree and paths it
  exercises. Never add historical counts to the latest count.
- A benchmark result is diagnostic until its dataset manifest, seed, hardware,
  compiler, execution mode, warmup, iterations, runner identity, and diagnostic
  state are frozen. It cannot close an optimization stage by itself.
- A progress percentage changes only after a roadmap-level stage audit. It must
  never be inferred from a coverage percentage, a test count, or one workload's
  latency.

The detailed Chinese roadmap retains dated audit history and the complete
Stage 0-10, P0, and C0-C7 work-package table. Keep both language pages aligned
when the status snapshot, execution order, or evidence boundary changes.
