## 2. Architectural Decisions and Boundaries

Target a general-purpose single-file graph database balancing point access, traversal, analysis, and transactional updates. Do not sacrifice other workloads for benchmark answers.

| Decision | Requirement |
|---|---|
| Preserve foundations | Single file, A/B publication, page COW, stable entity IDs/PageIds, relocation directories, snapshots, unified allocation/safe reclamation, StorageIO, explicit codecs, public ABI |
| Reduce read cost first | P1 does not change disk format; reuse components rather than adding a backend, removing directories, or replacing transactions |
| Prefer selective access | Reuse existing indexes/directories before persistent layout changes; do not force random index fetches for every scan |
| Local layout changes | P2/P3/P4 format changes require precise codecs, root ownership, atomic maintenance specifications, and runnable prototypes before production integration |
| Preserve correctness | Checksums, owner/generation/reference checks, primary-record consistency, read-your-writes, cancellation, error propagation; budget handling cannot swallow corruption |
| Platforms | Portable macOS/Linux/Windows production code; macOS execution required now, other platforms tested later by the user |
| Acceptance priorities | Necessary focused tests and measured benefit; no full unit suite, no coverage gate, no commit or push |

The current format specification explicitly excludes compatibility and migration. The default for a changed format is therefore **a newly created database with a new applicable version, and explicit rejection of old formats**. Do not add migration or delete user files. Envelope, Superblock, and local codec versions are separate spaces; change only affected versions and verify current source values. A different compatibility policy requires a separate requirement.

## 4. Staged Execution Plan

Dependency order: P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7. Each phase has five stable acceptance items. Close one attributable mechanism before introducing another. If a prerequisite fails, provide experiments and an alternative; do not silently skip work.

### P0: Freeze controls and attribute remaining costs

1. **P0.1 Provenance**: capture dirty status, relevant source SHA-256 hashes, Release compiler/options/dependencies, binary hash, hardware/OS, threads/cache/budgets. The control is the current uncommitted tree, not automatically HEAD. Preserve an isolated build/binary until comparison finishes. Never reset or stash user work.
2. **P0.2 Workload contracts**: align results, projection, indexes, transaction boundaries, and durability for point, scan, traversal, aggregate, read/write APIs. Freeze dataset manifests/seeds/hashes and a held-out set.
3. **P0.3 Warm attribution**: measure route lookup, directory/BTree decoding, CRC/identity verification, copying, buffer hits/misses, physical bytes, allocations, and lock waits; validate hotspots with stack sampling. Mark nested timers and do not sum them. Add minimal missing instrumentation without changing unprofiled semantics.
4. **P0.4 Control measurements**: acquire current ZYX control samples and available same-environment Kuzu samples; include empty/missing lookups to expose fixed costs. Historical cross-environment results do not substitute. If Kuzu cannot run, leave that comparison open while continuing independent internal attribution.
5. **P0.5 Decision record**: deliver hotspot shares, repeated-work evidence, call chains, benefit hypotheses, and falsification conditions. High logical counters alone do not prove which function dominates CPU.

Deliver provenance, raw samples/profiles, result-equivalence evidence, baseline comparisons, and attribution. P0 does not count as implementation speedup.

### P1: Reuse immutable decoded metadata

1. **P1.1 Interface/identity**: audit existing page caches/session and define a storage-internal read context carried through existing snapshot lifetimes. Keys cover database identity, publication generation, PageRef/PageId and owner, plus interpreting bootstrap/route context. Keep decoded pages and resolved child slots distinct; unresolved never means absent.
2. **P1.2 Minimal implementation**: reuse authenticated immutable decoded pages/routes, existing `findMany`, and page grouping. Integrate the point hot path before batches. The same resident key should not be decoded/verified repeatedly within a request. Decode once but resolve only requested logical children; never turn a point lookup into a tree-wide walk.
3. **P1.3 Lifetime/bounds**: query-owned, snapshot-bound, bounded existing management, no unbounded global cache. Values own data or valid pins. Account for containers, decoded payloads, and retained pins. Choose and document exact default capacity from P0 working sets/prototype RSS, not by arbitrarily raising budgets. Eviction permits rereads. Negative caching is context-local. Keep unpublished candidates, relocation, and integrity tooling on existing paths initially.
4. **P1.4 Tests**: old/new snapshots, equal IDs in different databases, wrong contexts, missing entries, relocation/reused pages, eviction, partial/full resolution, corruption, cancellation, budget exhaustion; preserve preceding-bootstrap candidate behavior. Select affected metadata/LocationDirectory/BTree/session cases.
5. **P1.5 Acceptance**: compare accesses, decodes, validation, physical bytes, allocations, unprofiled latency and RSS. Demonstrate reduced resident-key repetition and repeatable time benefit. Revert ineffective caching and attribute the next hotspot; code completion alone does not close the benefit item.

Reuse validation of the same immutable byte identity; do not bypass necessary first validation or change the existing external-file-mutation support boundary.

### P2: Selective label/type access and cardinality estimates

1. **P2.1 Existing-path audit**: inventory label/type indexes, schema support trees, and statistics; establish reusable query shapes before adding duplicate structures.
2. **P2.2 Candidate access**: first consume existing label/type candidate streams with batched reads. If missing, prototype existing B+Tree membership indexes ordered by `(LabelToken, NodeId)` and `(TypeToken, EdgeId)`, not per-node trees. Multi-label nodes have one member per label; values do not duplicate properties. Retain sequential scans at low selectivity.
3. **P2.3 Maintenance/statistics**: cover creation/deletion, label changes, supported type changes, import, detach delete, rollback, and overlay. Publish membership and truth atomically under COW. Derive statistics from final-state deltas, not operation count. Estimates guide planning, never exact query answers; missing/stale estimates fall back. New persistent roots require Catalog ownership, codec/version, and reclamation specifications first.
4. **P2.4 Tests**: no/multiple labels, duplicates, empty types, sparse/dense selection, old snapshots, repeated transactional edits, member/primary mismatch, cancellation, ordered continuation; preserve bag/result semantics versus scans.
5. **P2.5 Acceptance**: compare random candidate fetch cost against sequential scans. Use a simple measured cardinality/page-cost choice rather than benchmark-size thresholds. Selective work should scale with candidates; unselective work must retain the efficient path. Report extra writes and file size.

### P3: Property locality and column batches

1. **P3.1 Grouped acquisition**: group selected-column requests by property root/page/slot, acquire each page once, scatter back to logical order. Reuse verified_property_columns; avoid constructing row maps/strings just to convert them back to columns. Materialize complete entities only when needed.
2. **P3.2 Layout prototype**: if random property pages still dominate, prototype local typed blocks with stable owner/slot mapping, separate presence/null state, type tags, contiguous fixed values, variable offsets/lengths, and LargeValue references. Keep logical property interfaces. Do not introduce a second unverified property truth. Compare existing authoritative storage plus batching against authoritative local blocks for reads, updates, and space; do not switch without evidence.
3. **P3.3 Format/publication**: after prototype acceptance, specify exact byte layout, bounds, version, ownership, and checks. Field definitions and codec tests precede integration. Define coverage through current property roots; label changes must not relocate all properties. Publish new blocks/root references/entity visibility together and reclaim by snapshot safety. Optional min/max zone maps require complete type/comparison semantics; unknown or mixed values cannot be incorrectly pruned.
4. **P3.4 Tests**: missing versus NULL, numeric comparisons/types, strings/bytes/lists/maps, LargeValue, mixed types, duplicate/unsorted IDs, deleted slots, cross-page access, overflow/truncation/corruption, snapshots, overlay overrides, low budgets, early stop. Preserve the exact-index/primary-property mismatch regression.
5. **P3.5 Acceptance**: read only requested fields, explain page/byte/copy reductions, and validate wide-property/large-value held-outs. Report single-property update amplification, insert/delete cost, size, and RSS. Document adoption conditions and disclose write/space regressions.

Existing column interfaces are not proof of physical contiguous columns. If the layout is rejected, retain useful grouped acquisition and document the remaining scan bottleneck and alternative.

### P4: Local adjacency coverage and topology access

1. **P4.1 Contract**: current GlobalAdjacencyIndex uses `BLVL_EMPTY`, direction/node/EdgeId keys, and generation/last_edge_id continuation. Preserve key order and cursor semantics in the first prototype, adding only fixed-width NeighborId/TypeId payloads. Do not immediately substitute static CSR or add a second type-ordered adjacency structure.
2. **P4.2 Truth/integrity decision**: duplicated payloads can disagree with the primary edge despite valid checksums. By default retain batched primary verification and reuse its snapshot-local proof. This reduces repeated fetches, not necessarily first-traversal primary reads. Eliminating the first fetch requires a separately specified authoritative topology and equivalent validation protocol. Without it, keep verification; never delete tests or forge verified flags.
3. **P4.3 Local format implementation**: define exact key/value codec, leaf value layout, version rejection, root ownership/build/reclamation before integration. Publish both directions with the primary edge atomically. Preserve current self-loop direction behavior and individual EdgeIds for parallel edges. Cover writes/import/deletion and bounded high-degree pagination.
4. **P4.4 Tests**: zero/high degree, multiple types, self/parallel edges, continuation/direction, deletion/cancellation, overlay, old snapshots, relocation, directional mismatch, payload/primary mismatch, failed-commit recovery, budgets.
5. **P4.5 Acceptance**: first/repeated expansion, chain/star/skew, multihop, mixed updates; measure primary reads, metadata, RSS, write pages/bytes, and size. If validation or duplication cancels the benefit, do not ship coverage; record rejection and prefer joint adjacency/primary batching. Authoritative topology reorganization is not a default rewrite without evidence.

### P5: Batch execution, late materialization, and planning

1. **P5.1 Consumer inventory**: audit Filter/Project/Aggregate/Sort, JOIN/OPTIONAL MATCH/UNION, procedures, GDS, Vector, overlay, and maintenance. Separate migrated paths, real row-by-row fallback, and semantically necessary complete entities. Do not reimplement completed batching from stale ledgers.
2. **P5.2 Execution**: carry IDs, selection vectors, and requested columns; materialize only for output or expressions requiring complete entities. Restore order, duplicates, and path positions after grouped storage reads. Reuse bounded batches/budgets.
3. **P5.3 Factorization/costs**: only when multihop expansion dominates, implement grouped adjacency batches and delayed expansion. Preserve bag multiplicity, DISTINCT, aggregates, NULL, optional matches, path uniqueness, and LIMIT. Start with provably equivalent operator subsets and retain complete fallback. Use P2 estimates for anchor/join order and scan choices; stale estimates must not affect correctness.
4. **P5.4 Tests**: affected operators only, including mixed entity/scalar outputs, duplicates/NULL/order, aggregate counts, cancellation, low budgets, complex-expression fallback, procedure/GDS/Vector results; remove no public capability.
5. **P5.5 Acceptance**: materialized entities, copied bytes, intermediate rows/peak, allocations, latency; held-out degree, projection width, selectivity. Narrow wins require explainable semantic/cost eligibility, never query text or fixed IDs.

### P6: Writes, maintenance, and exact aggregates

1. **P6.1 Amplification attribution**: remeasure P2–P4 write pages/bytes, fsync, publication/reclamation, growth; identify repeated page work in planners/mutation executor, BTree, import, and maintenance.
2. **P6.2 General write batches**: group changes within one transaction by page/tree, reduce repeated COW/path rebuilds, reuse bulk support. Do not merge independent transactions, remove durability barriers, or report non-durable asynchronous completion as a speedup.
3. **P6.3 Exact counts**: consider type/label counts only for measured costly scans with eligible predicate-free semantics. Separate exact counts from P2 estimates. Define final-state deltas for writes/import/rollback/overlay, overflow, snapshots, and endpoint corruption detection. Keep scans if existing integrity contracts cannot be preserved; never return estimates for COUNT.
4. **P6.4 Tests**: atomicity, rollback, commit failure, reopen/recovery, old snapshots, constraint failures, repeated overlay updates, slot/page reclamation, count equivalence/overflow; affected storage/transaction selections only.
5. **P6.5 Acceptance**: small transactions, bulk import, updates/deletes, mixed reads/writes; disclose read/write/space tradeoffs. If no worthwhile write hotspot exists, document the audit and comparison rather than forcing a rewrite; unmet performance targets remain explicit.

### P7: Same-environment comparison and delivery

1. **P7.1 Focused integration**: combine actually affected module selections, ensure nonzero execution and cross-layer coverage. No full suite or coverage threshold.
2. **P7.2 Three-way provenance**: frozen current ZYX control, final ZYX, and Kuzu under identical environment/data. Old-architecture paper figures are separate historical context, not rankings with mismatched hardware/semantics. Missing binaries remain missing, never replaced with an unrelated commit.
3. **P7.3 Generality/resources**: complete representative held-out/write/space matrix in Section 5, result verification, and regression reruns. Report latency and throughput separately; single-query latency does not establish concurrent throughput.
4. **P7.4 Documentation/decisions**: synchronize languages, amended formats, and actual implementation state. Record adopted/rejected mechanisms, residual hotspots, remaining Kuzu gap; disclose repeatable regressions.
5. **P7.5 Cleanup/review**: verify final source/binary correspondence; remove only task-owned temporary databases/build copies/containers, retain compact evidence; check no benchmark cases, weakened budgets/validation, commits or pushes. Report every phase and measured benefit; task completion is not speedup.

Adoption requires correctness, expected work reduction, repeatable unprofiled benefit, and disclosed memory/write/space costs. ### P2.3 Maintenance and Statistics: Accepted

New-file initialization builds global NODE/EDGE members and complete per-token statistics before returning a closed handle. Existing-file opens do not scan implicitly. Missing completeness means unknown; only complete statistics treat absent tokens as zero. Labels require nonzero tokens; untyped edges use zero. Existing Catalog prefix `0x0D` subclasses 3/4 store token counts and 5/6 independent completeness version 1, reusing the root and `count + 1` encoding. Entity, member and Superblock layouts are unchanged.

Ordinary creation, label replacement, deletion and detach deletion fold to final-state deltas and publish with entities/members.
