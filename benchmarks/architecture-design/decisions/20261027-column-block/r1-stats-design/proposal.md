# R1 snapshot statistics: bounded design, not an implementation

## Evidence and limits

The historic medium full-node query was `MATCH (n) WHERE n.score>=900.0 RETURN count(n)` (`20261026-scan-supply-v2/allocation-probe.cpp` and `kuzu-profile.json`). The ZYX figure of 225000 is a direct-property input-row counter in one untimed work observation (`r0-work-model.json`). In Kuzu 0.11.3's separately instrumented PROFILE, 105000 is `SCAN_NODE_TABLE` **output** tuples, not its input, physical blocks read, or a count of skipped blocks; the following FILTER emitted 10076. Its scan mentions User, Post and Tag. A separate per-label diagnostic reports 100000 User rows, 120000 Post rows, User matches 10076 and Post score max below 900 with zero matches; Tag has no score property. Thus both traces refer to the intended same predicate and medium dataset, but their counters are at different operator boundaries and do not measure equivalent physical work. Post zero-match suggests an opportunity to study safely excluding work; neither 225000−105000 nor PROFILE timing proves zone-map/block skipping, its mechanism, device I/O savings or amortized gain. Preserve the diagnostic source and timing-quality limitations.

## Existing ownership and fences

- `MetadataSnapshotPin` owns a pinned superblock, registry state and read context until release (`MetadataSnapshotRegistry.hpp`); a native logical read snapshot owns the pin and its read session. The runtime normally opens a new logical snapshot for a query (`LogicalPlanReadRuntime.cpp`).
- Native `mutationFence()` derives a valid database/generation fence from the pinned superblock, and `bindingSchemaIdentity()` derives from that same pinned identity (`RelocatableLogicalGraphRead.cpp`). The hybrid context additionally uses the descriptor semantic generation and rejects or invalidates IO-epoch-based cached entries when the underlying data mutation epoch changes (`HybridPropertyReadContext.hpp`). No existing property min/max statistic with a proven equivalent version contract was identified.
- Transaction overlays maintain their own logical revision and read-your-writes fence. A base-snapshot summary alone is not authoritative for overlay writes; absent a separately proved overlay contract, the experimental path must decline the entire affected read before filtering.
- `ScanBatchReadGrant` is a synchronous, noncopyable authority for an exact pinned, verified source and ordered subset; it must not be replaced by a statistical claim. A summary can only say a verified source range *might* be skipped; it cannot authorize a result or suppress ROW/owner validation where that validation is required.
- Existing query-owned allocations use the materialization account; the buffer pool owns its shared pages and is not automatically a query allocation. Any new summary table, key, index, generation pin or retained copy must have an explicit owner and cap, reserve before allocation, and release after its last borrow. This proposal does not require charging already-owned shared pages a second time.

## Minimum testable candidate and alternatives

Start with an **ephemeral, query-owned** summary for an authenticated, immutable snapshot and one already visited bounded physical group and property token. It is created only as a by-product of an otherwise required complete, authenticated read; building it requires accounting for all decoded values, NULL/missing, mixed types and exceptional floats. It may be consulted only by a subsequent compatible scan within the same query and same still-live pin. On first visit, missing fields, unsupported types/operations, unknown encoding, invalid data, missing authentication, budget refusal, cancellation, reentry, epoch ambiguity, or any mismatch of pin/fence/schema/root/group/token/epoch, read normally. Do not reduce authorization to a summary hit; do not materialize large/complex values to build a summary.

Numeric min/max can reject a group only when the current comparison's established type and NaN semantics make **every possible visible value** a non-match. Mixed or uncertain comparisons decline. The proof must include exact equality and strict/inclusive boundary handling, -0/+0 and NaN, absence/NULL and all competing ROW paths. No query text, field name, row count or observed data distribution selects the path. There is no persisted layout change. This is an experimental design, not a claim that the present `ConservativeNumericBlock` is a valid stored statistic or that an existing group can currently be skipped.

Because ordinary queries open a fresh logical snapshot, a query-local table cannot automatically amortize construction across unrelated queries. It is worthwhile only if a real plan revisits the same group in one snapshot, and the cost of collecting/looking up and retaining summaries is below the measured work saved. A first-pass-only full scan has no such established advantage and is a stop condition, not a reason to introduce global caching. If actual workload needs cross-query reuse, a **separate architecture decision** must specify a bounded backend-owned budget, synchronization, pin lifetimes, generation keys and eviction, plus whether its stronger sharing/maintenance contract warrants format changes; none is authorized or selected here.

## Lifecycle and failure contract

Initial candidate has no shared or persisted summaries: a query snapshot releases all summary memory when it ends; old and new snapshots own separate tables. Updates/deletes/type changes publish a new generation, so a new query never inherits an old query's summary. IO epoch changes, lost validation and physical reuse invalidate the candidate conservatively even if the semantic generation appears unchanged. A live old pin remains valid only under the existing snapshot and IO/physical identity rules, never by an assumed generation number alone. Recovery/reopen creates an empty table; no recovered bytes are trusted as a statistic. Pin release and query cancellation destroy tables without retaining payloads or blocking reclamation. Overlay/revision and uncertain mutation cases fall back; no partial-result replay or suppressed exceptions is permitted.

## Frozen bounded validation before implementation

1. Select a real public QueryEngine plan that demonstrably revisits a group under the **same pin**, plus a single-pass control; otherwise stop this candidate. Record plan, authenticated owner/group events, actual group/column reads, decodes, result oracle and query resource accounting separately from timing.
2. Generate a bounded deterministic persistent fixture with unobserved seeds and representative group reuse, selectivity, dense/sparse and mixed/NULL/NaN values; keep distinct data for an independent holdout. Exercise same pin and old/new snapshots, mutation/delete/type/ROW routing, reopen/recovery and overlay fallback. No dataset-specific threshold. Record supported/declined rates and complete results with pruning enabled/disabled.
3. Instrument setup/build, memory peak/requested bytes, group/column reads, decoded values, skipped groups, fallback and invalidation separately; measure write and recovery maintenance where applicable. Explicitly count first-read construction and repeated read savings, not only a successful lookup.
4. Freeze realistic resource bounds and same-path disabled control before timing. The workload input must supply scan versus traversal/join versus write frequencies, repeat-scan opportunities, working-set scale and latency/throughput goals. Measure per-case process distributions and resource costs, not a chosen aggregate or an arbitrary hard gain threshold. Only compare same-window work/latency; retain raw samples and failed cases.
5. Stop if a snapshot cannot be fenced, any stale/ambiguous statistic can cause skipping, summary ownership or fallback cannot be bounded, net work is merely shifted, first-visit cost dominates plausible reuse, or a representative workload consistently regresses. Do not expand cache/format merely to obtain a passing microbenchmark.

Open decisions for the parent/user: whether a real workload contains repeated same-snapshot scans at all and the desired scan/traversal/write mix and scale; whether a later independently justified backend-wide cache is in scope (not required for this no-format proposal). No data download, benchmark run or implementation is authorized by this design alone.
