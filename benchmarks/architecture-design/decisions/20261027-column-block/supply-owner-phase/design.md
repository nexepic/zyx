# Same-snapshot owner authentication: evidence and candidate boundary

The frozen identity protocol and test-only observations establish a bounded structural repetition for an explicitly pinned snapshot and one optimized plan (`Aggregate -> Filter -> NodeScan`). The refined observer labels the property-cell/column read entry points as `selected` and `nodePropertyIsNonNull` as `nonnull`. For the old snapshot, 191 matching owners each had one check in each stage; after updating owner 1, 192 owners did so in the new snapshot. The complete result and unmodified mutation fence were verified for each supplied pin. The samples record Entity Map and competing ROW checks, not elapsed time. The optimizer here is invoked without the QueryEngine statistics provider, so this plan is not asserted to be identical to the earlier public QueryEngine experiment.

The stages have different data requirements. Selected-property filtering and aggregation may need values; `COUNT(property)` ordinarily uses a presence/non-NULL probe specifically to avoid copying arbitrary large or complex payloads. Simply adding COUNT's property to the selected value list can change memory pressure and fail a query that previously fit its budget. The existing two-group membership cache binds authenticated owner bits to its read context and mutation epoch. A scan batch grant is synchronous and explicitly must not escape its visitor; a downstream result row cannot be treated as possessing that grant.

A candidate worth prototyping is a **single synchronous, budget-admitted property window** which accepts value requests and non-NULL-only requests together, and performs shared owner-route authentication once for that exact window. It must return non-NULL results without copying complete large/complex values. This is a capability proposal, not a currently available contract and not an implementation in this change.

Before exposing such a capability, establish:

1. Scope and identity: authority is minted by the same backend/context, pinned snapshot and descriptor generation, owner kind, exact sorted owner set and observed IO epoch. It cannot be copied to arbitrary rows, other readers, later callbacks, another query or another snapshot. On mutation/epoch change it is reacquired or declines; old pins retain their own immutable data.
2. Authority: retain Entity Map liveness, competing ROW validation, group/column and presence authentication; tokens or counts must not stand in for owner authority. Do not equate logically matching IDs with a verified source. ROW, cold, extension and complex/large values require their existing semantics.
3. Admission and lifecycle: bound owners and keys before producer access; charge identity/presence buffers to the same query resource account before allocation. Enforce existing maximum work, guard and cancellation cadence. Borrows live only during the synchronous callback. Reentry cannot reuse a partially built window. Exceptions or a refusal before publication discard private results and never replay delivered effects; after publication errors propagate. If required admission or capability is unavailable, preserve the established probe path before consumer effects.
4. Completeness: missing, NULL, mixed numeric/string/complex types, NaN and duplicate/unordered requests must match the existing oracle. Do not materialize COUNT-only large payloads, alter read-your-writes behavior, weaken recovery/reopen/old-pin tests, or expand the on-disk format. Partial output, ambiguous authority or inconsistent epoch must fail closed.
5. Falsifiable work test: on an independent window with at least three logical groups, show that the same selected owners' Entity Map/ROW checks fall from two to one per owner while field-specific checks still execute, with exact old/new snapshot results. Include sparse and repeated IDs, no-match/partial selections, decline and tiny budgets; count additional sorting, copying, allocations, reads and fallback. If equivalent work merely moves layers, reject the candidate.
6. Only after affected module tests pass, freeze a bounded no-coverage optimized comparison with the same generated persistent inputs, query semantics, budget and same-path disabled control; include alternative plans, complex COUNT-only values, read/write/reopen costs and guard workloads. Preserve all samples and report instability. This does not replace the old formal protocol or establish production adoption.

Current status: **no reusable authority or combined presence interface has been implemented**. Existing evidence confirms duplicated checks, but not the safety or net value of bypassing them. Do not enlarge the cache to cover these fixtures or introduce query-text, fixed-property or input-size branches. Default experimental COUNT remains off. Until the combined capability's resource and callback contract is implemented and validated, the existing scalar presence path remains authoritative.

## First implementation slice: optional contract and private receiver

The storage-neutral optional `LogicalGraphJointPropertyReadProvider` contract and query-local `JointPropertyWindow` receiver are implemented as an unconnected first slice. The provider is discovered from the exact snapshot; its absence or a decline before callbacks retains the existing path. The receiver enforces sorted unique bounded IDs, bounded value/presence column counts, budget-backed private buffers, explicit source admission before first output, per-presence-cell exactly-once and completeness, callback reentry and failed/expired state, and snapshot-fence/schema checks. Only sealed private output can be read. Non-NULL results are booleans and the provider contract forbids decoding large/complex payloads merely for presence. A consumer cannot infer actual payload from the presence bit. These contracts do not themselves establish native storage authority or prevent an incorrect provider from underreporting admission; a real provider must enforce those obligations.

The public QueryEngine's own `buildPlan` and execution on the 192-node read-only fixture produced `Aggregate -> Filter -> NodeScan` and independently returned the complete oracle; 191 owners were authenticated once in selected-value read and once in non-NULL probe. This confirms the observed shape at the public entry for that fixture, not all plans or data. Its captured test-only events remain diagnostic, not a time measurement.

No production snapshot implements the optional interface yet, and no aggregate/scan consumes it. Thus neither duplicated checks nor production work have been reduced; the new interface and receiver are not grounds for an on/off benchmark. Next implement an opt-in native producer and bounded consumer within the scan grant only after proving whether its callback lifetime permits the two operations together. Required integration cases remain competing ROW routes, actual LargeValue, epoch changes and retained old pins, admission denial and rollback, reentry/cancel/exception without replay, and sparse/unordered/duplicate fallback. The provider may return false only before any callback. A later bounded Release on/off experiment is meaningful only after an independent work-count test establishes elimination and the controls exercise the same source path.

## Native integration boundary identified

The current `LogicalGraphNodeScanProvider::NodeScanPropertySource` supplies value and typed-run callbacks only. In the certified native path, `ScanBatchReadGrant::read` activates `ScanBatchReadScope` solely around that fixed value-source call and revokes it on return. A later call to `nodePropertyIsNonNull` is outside that grant. The scalar non-NULL API accepts no source-admission callback; hybrid LargeValue inspection uses scoped owned-allocation reservations and may use the snapshot's memory owner. Consequently, invoking the existing scalar probe after the source and assuming a still-valid grant or a pre-admitted query budget is not a safe implementation.

The next native slice must introduce an optional joint **scan-source capability**, separate from the existing source so unsupported implementations can decline before any output. It should execute both selected values and non-NULL-only probes inside the same `grant.read` scope, with an explicitly accounted source workspace and an admission interface for the actual presence/large-value inspection; it must not allow the source callback or its authority to escape. The executor must consume the resulting presence bits privately, preserve COUNT's non-materializing behavior, and fall back within the current batch before consumer effects on an optional capability/admission refusal. A complete producer/consumer plus actual storage tests is required before a deterministic work-reduction claim or pre-registered no-coverage on/off comparison. This is unfinished engineering, not a platform permission denial.

The private receiver was additionally hardened against a provider catching a source-admission or callback exception and returning a decline: it records and rethrows the first original exception, rather than silently retrying or changing a budget/cancellation failure into a fallback. This remains an interface-level fake-provider validation and does not establish native integration.

## Experimental presence accounting audit (partial)

The opt-in direct probe installs the caller's `UnmanagedAllocationResource` as an `OwnedAllocationScope` and uses a local `NativeReadSession`; the session and its PMR caches are destroyed before that scope ends. Hybrid `exists` creates `OwnedHeapReservation`s for boundary and references. Large-field inspection reserves the manifest, range and directory separately, before their buffers; `verifyContent` authenticates all chunks and hashes content without creating a full owning output, while a subsequent range reads the null header. These reservations unwind on exceptions. The inspection is not constant I/O: verifying the value traverses its content.

A concrete legacy ROW gap remains: `PropertyCollectionRootStore::decodeEntityPropertyExists` calls `readLargeValuePropertyDirectory` without a buffer admission and `PropertyCollectionRootScanCursor::readSelectedPresenceLocation` copies a page slot into a standard vector. Merely installing a PMR owner does not govern these buffers. `BudgetedPresenceScope` now rejects the experimental probe before either ROW fallback instead of presenting that route as budgeted; callers must retain the original path. This applies to the new probe only. It does not fix legacy ROW accounting or prove all catalog, page and snapshot allocations are attributable to the query: their allocation contracts still require auditing. In particular, current tests do not establish complete same-budget equivalence or a production-safe source.

The direct probe has no executor consumer and is not an optimization adoption. Its API remains experimental, and the proposed joint source must not be connected until resource ownership and refusal-before-effects are verified. An 8 KiB input test alone does not prove the cost or allocation bound for larger values. No timing or reduced-work claim follows from this audit.

Follow-up: catalog lookup uses `OwnedAllocationScope` for property-name keys and B-tree owned containers, but reverse-name conversion constructs a standard string and calls `admitScopedPropertyString` only when a `property_decode::AllocationScope` exists. The experimental probe now installs that scope with a cumulative `OwnedHeapReservation`, charging before each reported standard allocation and releasing at the end of the synchronous probe; nested checkpoint propagation remains available. This conservative credit can exceed simultaneous live bytes. B-tree and page/cache paths still need a complete same-account audit before source integration. The earlier ROW fixture attempt opened a BUILDING image as a complete backend and failed as designed; the separate normal-backend fixture cannot initialize when this build enables SCAN format. A direct `PropertyCollectionRootStore` test against the original real ROW source is being used instead; it establishes only storage-level refusal and fallback, not executor-side replay safety.

The replacement real ROW test constructs a native ROW with `NativeGraphWritePlanner`, confirms experimental refusal before its local result effect, verifies zero remaining budget and checks the ordinary presence path returns true. The SCAN large-value and ROW tests plus six joint-window tests passed (8 total; `/tmp/zyx-presence-row4-test.log`). The effect checked here is a local test counter; no aggregate was wired, so it is not proof of executor-side rollback. Two prior fixture failures are retained in `/tmp/zyx-presence-row-test.log` and `/tmp/zyx-presence-row2-test.log`.

## 2026-10-27 feasibility decision: defer the joint candidate

This decision does not assert that all native SCAN inputs are impossible under budget. The existing resource contract counts retained query materialization and explicit transient reservations, not all process RSS. `MaterializedByteBudget` accounts requested bytes and may share a query resource account. The native scan's 128 KiB workspace is admitted before source access; source additions are charged through its admission callback. Private lookup/selection, `DirectPropertyColumns`, proposed presence bits and any new per-window session state require the same query account before allocation. The existing buffer pool owns authenticated shared pages (`PropertyCollectionRootStore.cpp`, comment before the optional retained-page copy); borrowed shared pages are not a new query-owned page buffer, and are not automatically double-charged. Query-owned copies and retained pins remain subject to the existing specific contracts. The prior statement that all B-tree/page allocations needed a new single-account audit before any progress was too broad.

The existing `LogicalGraphNodeScanProvider::NodeScanPropertySource` supplies only value callbacks, and `ScanBatchReadGrant::read` enters and leaves the authorization within that source invocation. `NodeSupplyAndSorting.inc` seals and filters private values after that call. `AggregateOperator.inc` rejects direct aggregate eligibility for COUNT-only properties to avoid materializing payloads and otherwise probes presence in its later row loop, where aggregation can already have effects. The experimental one-probe local session avoids lifetime leakage but repeats session/catalog setup per owner and is not a joint source; its test does not establish net work reduction. A safe implementation needs a source continuation that keeps grant scope during filtering and payload-free presence reads, bounded query-accounted state and a per-batch pre-effect refusal protocol, including ROW and pressure fallback. This is broader than swapping a callback and has not been implemented or measured. Adopt no new path until those contracts receive a separate design decision and real end-to-end evidence; keep the experimental objects unused by default. Deferral is a risk/scope decision, not proof of impossibility or a failed performance result.

The existing R0 key-scratch experiment is a separate demonstrated reduction of allocation work (125998 to 26618 in its recorded workload, full oracle and 37 related tests), but still serializes and hashes per input row. R2's typed composite-key/no-allocation lookup is a supported next investigation, not a proven speedup; its correctness, budgets, hit/fallback accounting and an independently frozen work comparison must precede adoption. No fresh implementation or timing result is claimed by this decision.
