# Bounded persistent COUNT fusion experiment

The preregistered `protocol.json` was saved before these results. `receipt.json` records the protocol and executable hashes and all twelve process exits; the twelve `run-*.log` files retain every measured sample, full-result check and separate untimed path counters. `summary.json` and `analyze.py` retain all 12 scenarios. The build was CMake Release with `-O3 -DNDEBUG`, LLVM coverage disabled, experimental SCAN/HYBRID enabled, and experimental streaming COUNT disabled by default. A test-only thread-local switch selected the two arms; both used the same generated, reopened database, query, result consumption and resource bounds.

All twelve process/scenario runs completed and every timed and untimed invocation matched the independently calculated oracle. All 72 separate work observations confirmed that the enabled arm streamed the candidate rows and the disabled arm materialized them through the prior direct-column path. `regression.log` contains 18 passing affected tests, including default-disabled and explicitly enabled coverage.

Pooled control/fusion median ratios across all cases ranged from 0.733 to 1.358; above one favors fusion. At 128 rows with mixed types and threshold 129, the pooled ratio was 0.733 and process ratios were 0.791, 1.085 and 0.584. At 512 rows, pooled ratios ranged from 1.020 to 1.358, but several individual processes still favored control. The mixed-type highest threshold is not a zero-match case because PropertyValue compares types using its established ordering; pure integer highest-threshold cases are zero-match. Full results and per-process ratios are in `summary.json`; no samples were dropped. Six samples per process/arm are insufficient for stable P95 inference.

Peak RSS reported by `wait4` was 34432 KiB in each whole process, including test runner, offline fixture construction, clone and reopen; it does not isolate query or arm costs and may include pre-exec child state. Query-level allocation counts and per-arm RSS were not instrumented. These measurements use warm reopened synthetic images, 128/512 nodes, one thread and a test build with fault hooks; they do not establish performance for large/cold graphs, writes, concurrency, other operators or default ROW. Build/maintenance and conversion costs were not independently attributed.

Decision: keep streaming COUNT disabled by default. This bounded result shows no consistent net benefit across the preregistered cases, with material mixed-type regressions and process variability. Retain the experiment and its evidence; do not claim general adoption, R1 completion, Kuzu parity or a historical formal-window result. Further evaluation requires preregistered representative workload sizes and independent query allocation/resource measurements; no threshold or dataset-specific routing may be derived from these observations.
