# Independent group-key investigation

R1 is not complete. This is a bounded, independently reviewable R2 candidate experiment, not an R2 exit or an adoption decision. The previous `key-scratch/work-receipt.json` counts 125998 vs 26618 allocations and validates a complete multi-key oracle in an untimed persistent SCAN worker. The worker includes open, copy, query and close; RSS and I/O are whole-process values. Its compile records show O3/NDEBUG for the runtime, and O1 for test code. It does not establish query latency, memory reduction or a general workload benefit.

Hypothesis: even after scratch allocation reuse, repeated groups serialize and hash a complete key once per accepted row; heterogeneous lookup against existing owned encoded keys may avoid building a temporary encoded key while retaining the existing canonical encoding. Test-only counters must report accepted serialized tuples and bytes, hit/miss counts, with complete result oracle and no timing inference. The first diagnostic is the existing `RepeatedCompositeKeysPreserveOwnedGroupsAcrossScratchReuse` test, and is not holdout data. Any later new implementation requires a separate frozen independent dataset and control before comparison.

Semantic contract: distinguish types exactly as the existing `appendDistinctPropertyValue` encoding; missing/NULL use existing column semantics, negative and positive zero match, NaN bit handling follows the existing encoding rather than assuming IEEE equality; ordered list elements and sorted map keys retain their current encoding, strings and complex data cannot outlive borrowed views. Hash collisions must resolve by complete encoded-key comparison. New groups own keys and payloads; temporary borrows remain within the synchronous callback. All added retained and scratch allocations use the query materialization budget, admission precedes allocation, guard/cancellation cadence and exception propagation remain intact, and unsupported shapes fall back before group mutations with identical results. No fixed property names, query text or data-size branches. Compare candidate and control at equal input and budget and report hit/fallback and resource costs; do not infer speed from counters.

The allocation probe's `multi_key_group` template groups User country and age and orders the result. This identifies the measured workload only; it must not select an implementation. The copied whole-worker receipt does not itself identify which database copy was used, so dataset size and distribution are not inferred from it.

Diagnostic result (test-hooks build, not timing): 96 accepted rows, 6 distinct groups, 90 lookup hits and 6 misses, 6080 encoded bytes built; the direct and legacy paths returned identical six groups of 16. This confirms repeated encoding on this bounded fixture only. The entire 6080 bytes are not necessarily avoidable: heterogeneous hashing must inspect key bytes and collision checking must compare them. No candidate is implemented or accepted by this observation. The test log is `/tmp/zyx-group-key-work-test.log`.

## Frozen independent validation 2026-10-27

Use generated two- and three-key logical plans through the existing direct-column fixture, with deterministic integer permutation `(row * 37 + 19)`; 240 rows. Cases: all unique, six repeating tuples, mixed missing/NULL/bool/int/double/string including empty, embedded NUL and 1 KiB strings, and complex list values that force ordinary fallback. Compare the entire sorted result against the same query with experiment disabled, additionally check group cardinality and row-count sum. Include +0/-0 and NaN bit patterns as encoded by the existing path; never use NaN's ordinary equality as oracle. Force hash collisions through a test-only hook and require unchanged full results. ## Initial experimental implementation and evidence

`ZYX_EXPERIMENTAL_BORROWED_GROUP_KEY` defaults OFF. The direct-column aggregate can build a budgeted secondary hash index whose entries borrow pointers to owned canonical keys in the existing group map; supported primitive/null cells hash without constructing a temporary key, then compare the complete canonical byte stream to resolve collisions. Unsupported complex cells keep the existing serializer. The index adds per-group allocation, and its allocation failure propagates; identical behavior under all constrained budgets and pre-effect fallback are not yet established. Neither this initial code nor its tests is an adoption decision.

The pre-registered repeated and unique 240-row test passed on the test-hooks build, including forced collisions and complete same-input control results: repeated input serialized 6 keys, unique input serialized 240. An additional mixed test passed for missing/NULL, bool/int, +0/-0, two NaN bit patterns, embedded NUL and a list fallback with forced collisions. A first test run erroneously used the fixture's 8-node limit for 11 input nodes; both arms returned eight and the test failed. The limit was corrected, preserving the failed log `/tmp/zyx-borrowed-key-mixed-tests.log`. The subsequent 39 related tests passed in `/tmp/zyx-borrowed-key-final-tests.log`; not every existing test explicitly enables the new experiment. No non-instrumented timing, persistent QueryEngine comparison, explicit cancellation/exception/reentry and small-budget candidate tests, or measured index resource/maintenance costs have yet been completed. R1 and R2 remain open.

## Follow-up contract checks

The experimental index now uses its own `BudgetMemoryResource` in the same query materialization budget. It applies only to multi-key direct grouping; single-key partial count remains on its prior path. A new index entry is admitted before creating its group. If this optional admission throws `MaterializedByteLimitExceeded`, the index is discarded and the existing encoded lookup continues. A test-only injected refusal after two index entries verifies a full result matching control and one fallback, including prior groups. It does not establish that every real budget failure falls back: other aggregate allocations can and must still fail. With a real 16384-byte budget, the test observed aggregate group-vector admission failure after an index entry; it is not evidence that the index itself caused that failure.

An enabled-path guard exception test fires after index allocation and a following query succeeds; it does not separately prove asynchronous cancellation or reentrant callbacks. Test-only index resource peak in the 240-row fixture was 296 bytes for six groups and 9736 bytes for 240 groups, excluding canonical keys and other aggregate memory; it is requested allocator bytes, not query RSS. Forced collisions preserved the full result. The latest 42 relevant tests passed (`/tmp/zyx-borrowed-final4-tests.log`); the previous stricter exception-type attempt failed because the existing group-vector limit reports a `std::runtime_error` and is preserved in `/tmp/zyx-borrowed-final2-tests.log`. No non-instrumented persistent timing or adoption claim is made. Before a performance comparison, separately test cancellation/reentrancy and source lifetimes under repeated batches and verify both arms use identical limits and complete oracles.

## Cross-batch and asynchronous guard tests

The enabled and default arms each completed a 600-row, multiple-batch fixture with an observer-triggered nested execution, complete three-group counts, retained old output after source modification and a subsequent query. A separate test delivered a signal from a second thread through the existing `QueryGuard` sampler, then verified a later query succeeds in both arms. This tests the embedding's guard-sampler cancellation mechanism, not a distinct public cancellation API. All seven candidate-specific tests passed in `/tmp/zyx-borrowed-async-tests.log`.
