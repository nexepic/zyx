# 维护工作区与标准容器堆计费

本记录是组件交付，不是 S5.3/S5.4/S5.5/S6.1/S6.3 整项验收。进度仍为 22/34（64.7%）。

原生 `maximum_reclaim_workspace_bytes` 默认 8 MiB，控制三种显式回收入口和后台维护每次执行的 MAINTENANCE 预付额度。显式回收在发布锁外申请；后台任务在申请不到额度或创建工作区遇到 `bad_alloc` 时延后，未触及持久状态，因此不触发不确定写入标记。进入任务后的真实错误仍沿用失败关闭路径。作用域内顺序读取绕过缓存准入并保留脏页可见性。工作区控制对象本身使用拥有资源的分配前缀。服务析构先停止线程，再销毁计数器、协调器和工作区工厂。

LargeValue、标量索引树、向量原始页/码本/派生对象/Manifest 的内部 map/set 及退休计划容器使用拥有资源的分配器。嵌套集合和页身份数组也继承作用域；已有公共接口返回的标准容器、schema/Manifest/codec 内部载荷仍需继续治理。不能把 8 MiB 工作区等同于这些路径全部堆内存的硬上限，也尚未解决整个 Catalog 扫描和持续写入下的持久积压问题。

标准容器堆模型统一统计属性及结果的 vector/string/hash 结构：MSVC 每桶两个迭代器、链表哨兵、调试代理，以及 x86/x64 大分配对齐前缀。依据是上一检查点归档的固定 MSVC 源码。查询结果 API 在构造空容器前申请三个调试代理的额度；结果数组扩容申请新旧重叠，最终读取收集器也包含对齐前缀。模型描述 allocator 请求及保守节点大小，不是 malloc 元数据或 RSS。MSVC 一般调试容器在 noexcept 构造中分配代理的问题仍未全面解决，未运行 Windows/macOS 验证。

386 个启用的定向测试、22 个 suite 全部通过。新测试覆盖真实原生后台工作区额度耗尽后的延期/恢复、工作区在发布锁外创建、作用域分配/顺序读取、MAINTENANCE 计费归还、满 CACHE 回收和小工作区零写入拒绝。独立堆探针通过 16 种属性/结果形状，最大观察到 272,912 个申请字节；这仅是 Linux/libstdc++ 执行证据。完整测试列表、源码哈希和日志见 proof.json 及 module-evidence.tar.gz。没有全量测试或新的性能采样。
