# Partitioned DISTINCT and query scratch ownership

Component delivery only: S5.3/S5.4/S5.5/S6.1/S6.3 remain unaccepted, at 22/34 (64.7%).

With native scratch permission and at least 4 MiB of actual execution allowance, Project DISTINCT and UNION DISTINCT use a bounded key set. Small sets remain resident. At one eighth of the allowance, or when shared output reduces transition headroom, keys move to eight in-file hash partitions. Fixed Bloom filters reject definite misses only; possible matches require exact bytes. A regression uses distinct keys sharing both Bloom bits and a partition. First-occurrence order is preserved without input replay or physical-pointer serialization. Block versions, counts, lengths, routing and tails are validated; cleanup routes are allocated before fragment publication. PMR tables, partition/Bloom/block/route capacities and returned read bytes are charged to execution; disk and handles have separate finite bounds. Grouped aggregation, hash joins and other operators still have explicit in-memory rejection paths, so this does not claim universal spill.

Sort and DISTINCT pass the existing query account into native scratch. Handle grants consume the same query ceiling, remaining charged for a retained finished session until destruction. The two-argument entry point remains. Providers without explicit account support reject non-null owners. Query and scratch entry points reject CACHE/WRITE/MAINTENANCE/CODE accounts even within the same database, preserving maintenance credit. Opaque reads move their owned payload instead of copying it.

A wide-key test exposed raw backticks retained in declarations while references were decoded. Variable declarations now reuse normalizeSymbolicName, with null/plain/space/doubled-backtick coverage and no grammar edit. Under 8 MiB, a large direct-row result initially hit key-table admission; the headroom fix moves rejection to final-result retention, as confirmed by an isolated throw trace. A native regression checks query/scratch refunds, unchanged graph and successful subsequent execution. A 24,000-input/12,000-distinct collection passed; the permanent test uses wide keys to shorten execution while still verifying actual file writes and complete ordered output.

All 1,971 enabled selected tests across 76 suites passed. One existing disabled scale case was not run; two expensive native sort integrations were excluded from this round. Another 77 contract tests and 55 subsequent parser compile/tests passed. An isolated worker sampled 16 of 41,881 normal DISTINCT allocations; together with four terminal cases, all 20 passed. This was sampling, not exhaustive fault coverage. See proof.json/module-evidence.tar.gz for source identities and evidence.

Protected cleanup, public/nested payloads, other workspaces, private write data, durable backlog and final regression/fault acceptance remain pending. No full suite, new performance campaign or performance-win claim.
