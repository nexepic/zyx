# S0.4 热点与反证报告

S0.4 的调查报告交付完成；不代表性能目标通过。总进度 27/34（79.4%），本轮 3/5。S0.3 完整工作负载矩阵与 S5.5 稳态仍继续。

正式读取比较覆盖 20 个可比较场景、24 个独立配置进程、1200 个样本，三轮结果 oracle 通过；另 3 项索引场景保留不可测原因。当前版 medium 扫描／聚合／Top-K 三轮进程 P50 中位数分别为 3055.525／3203.310／3303.220 ms，Kuzu 为 2.142／3.629／4.016 ms。远未达到 Kuzu 目标。冻结控制版输入失败，不能证明相对控制版降低 10%；不把调查完成计作性能胜出。

标签筛选累计约 3.62 GB checksum，仅约 37.6 MB 缓冲池读取，却发生约 87 万次文件大小检查。聚合和 Top-K 有同样数量级的重复目录读取与校验。一次点读也累计约 55 MB checksum。CPU 样本与分配调用栈反复出现 crc32_z、MetadataPageRouteLeafCodec::decode、CatalogRadix 校验和 MetadataPageReadContext/BTree 容器。计数支持重复认证、目录解析和短命分配是值得关注的成本；不能仅据采样排除其他成本，也没有删除首次必要验证。

CPU、堆和原生计数分别采集。组合 CPU/heap 采集触发原有 30 秒查询超时，失败保留。最终五类查询均完成独立采样并验证结果。整进程 CPU 采样含打开、克隆和预热；采集器 CPU 秒仅约为 OS user+system 的 1%，计时不可信，因此只将函数 PC 分布作为低置信度定性线索，不声称完整覆盖或精确查询份额。OS 实际 CPU 时间独立保留。嵌套计时不相加。

堆分配只采约 200ms 的墙钟窗口，保留真实调用栈／实例／字节；不外推整条查询总量。窗口内数字不是查询峰值或 RSS。Linux 进程 I/O 与数据库计数分别报告；gprofng I/O 采集在本机不可用，没有用零值代替。

三进程、每机制三次预热和十次采样，共 150 个机制样本逐值验证。原生字段读取 4096 值为 3.624 ms；同一已物化输入上，含转换的 typed filter 为 0.06333 ms，generic 为 0.03990 ms，typed 为 1.587 倍、反而更慢。该形状的转换型内核收益主张被反证，不据此扩大采用范围；已有 generic fallback 保留，后续生产性能准入仍归 S2.5。

完整排序返回 4096 行（17.052 ms），Top-K 返回 128 行（11.816 ms）。输出量不同，不用它们宣称端到端提升 10%、2x 或 10x。原生读取、类型化转换、generic 和排序均以完整实际值验证，不拿机制数字替代正式读取比较。

探针零值边界错误在采样前修正，旧失败留档；只改诊断入口，未改数据库核心、格式、64MiB 物化预算或 durability。受影响生产源码仍与已通过 2628 项模块测试的冻结版本一致。S0.4 按报告与反证交付验收，不借此验收 S2.5/S3.5/S4.4/S5.5/S6.2。
