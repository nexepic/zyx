# File capacity and scratch outcomes

Component implementation; no new delivery accepted, still 22/34 (64.7%). Native options provide a finite immutable maximum_database_file_bytes (default 1 TiB). Complete raw/typed/batched/control/append/reservation ranges are checked before cache mutation or I/O, including test-hook page loops. Existing embedding constructors retain their former behavior. Writable opens reject an existing file above the ceiling before reconciliation; physical read-only inspection remains available. Writable aliases of one opened physical database must use identical active limits. A retained old limit value cannot contaminate a reused registry slot. The ceiling is not persisted and can be reconfigured once all writable owners close.

A pinned-snapshot workload changes a scalar in a 6,000-byte property collection until the configured file ceiling refuses a candidate. Its old snapshot and last successfully published value remain complete. Releasing the pin, reopening and explicitly performing bounded LargeValue reclamation permits another write under the same ceiling. The initial test retried without reclamation and failed because retired ownership does not automatically reclaim all unreachable LargeValues; that failure is retained. This test does not promise automatic reclamation, every maintenance operation's headroom, or a universal steady-state bound.

Scratch previously treated every configured capacity refusal as uncertain I/O, which blocked cleanup of already-owned handles. A dedicated StorageFileLimitExceeded preserves the distinction from real OS errors. NativeBulkRunStore reports NativeBulkRunCapacityDenied only when namespace reservation cannot have published fragment ownership, or when the durable Catalog root remains unchanged across the physical-allocation attempt. Otherwise the existing reopen/recovery requirement remains. The session refunds its pending disk credit only for that proven unpublished refusal, retaining earlier handles and allowing quota reuse while an ordinary graph pin remains alive.

Fragment receipt storage is allocated before publication. Physical allocation and extent allocation now move the returned reservation vector, avoiding a fallible copy after metadata publication. A control compiled with just those preceding copy expressions performs 1,699 allocations rather than 1,698 on the fixed scratch workload. Failing the removed last allocation makes that control require recovery; the fixed code does not reach it and returns complete handles. This is an availability/allocation observation, not a latency measurement or claim that every publication path is allocation-free.

All 1,625 explicitly selected module tests in 66 suites pass. All 1,698 reached scratch-write heap allocation failures pass, including complete successful handles, safe prior handles where no fence is required, conservative recovery where necessary, unchanged user data/fence, reusable one-segment quota and reopen/integrity. Four terminal cases and 32 real scratch-crash cycles pass; each recovered file is 1,572,864 bytes and read-only orphan inspection preserves its SHA-256. The current worker is frozen by SHA-256; the previous broader 4,346-fault matrix belongs to the preceding checkpoint and is not relabelled as current-source evidence. No full test suite or performance campaign ran.

The StorageIO pin telemetry test was corrected for the earlier copy-read race fix: copying a page no longer publishes an external pin, so two explicit pins of the same page count one distinct physical pin; a later copied second page adds none. The counter implementation and resource limits were not relaxed to satisfy that assertion.
