# S3.3 approved ROW placement in production

Native RelocatableStorageBackend now enables the S3.2 cost-admitted ROW chunk policy by default. Ordinary NativeGraphWritePlanner property writes pass the policy into PropertyCollectionRootStore. Newly materialized eligible RAW collections use the bounded requested cuts; compressed/small/over-wide/non-admitted collections and generic streamed/bulk callers retain the existing valid ROW extent path. The caller can explicitly disable the placement optimization. Existing immutable references and content-dedup hits are read in their original layout; no background repacking or format migration occurs.

The bilingual native single-file specification now separates the implemented per-key mutation API from remaining whole-owner rewrite amplification, documents the actual ROW policy and limits, and replaces the old fixed 16–64 KiB chunk assumption with the existing explicit-offset Manifest contract. All supported uniform extent classes remain valid. No format version, page type, root namespace or Driver ABI change is required: the cuts are transient writer options, and readers authenticate both layouts using their normal manifest/page owner/generation/checksum protocol. The owner-keyed Property Directory remains the unique authority; MIXED/column containers are not activated.

Current-source verification passed **145 selected tests**: 130 property/LargeValue/native-lifecycle tests, seven S2.4 actual native semantics cases and eight bound-program native integrations. A new public Database/QueryEngine test confirms the default policy, selected scan/aggregate, non-null COUNT, SET results, large owning output after close and reopen. Fresh default-enabled native smoke passed **916 complete-result commands across 13 families**, including writes, large values, old snapshots, physical/logical readonly, cancellation and low budgets. Proof and local raw evidence are retained.

Accept S3.3 for the approved conditional ROW placement and specification update. Complete owner replacement can still re-encode unrelated large bytes, the data/Manifest/entry-cost estimate does not prove a universal shared-pool/file-size bound, and process-global memory remains S5 work. The dedicated fault matrix is S3.4; O3/O5 performance/resource and steady-state acceptance remain S3.5/final-window work. No full suite or comparative timing was run.
