# Property prefetch with a non-admitting source

In native macOS run 41787248888, source da4a6c2aaa3ff1770ef598693f0308d785e4045f. With a 4,096-byte query limit and a source reporting `supportsPropertyReadAdmission() == false`, each attempted two-node batch returned 6,016 bytes of payload, with 6,168 bytes total estimated working set, before pressure split the rows and fetched them again. Three split events explain the observed duplicate reads; charging only after this allocation cannot establish a strict pre-allocation limit.

A temporary Linux copy of the existing exact-once test retained all assertions but swept budgets 4,500, 5,000, 5,500, 6,000, 6,500 and 100,000 instead of the original two values. The 5,000, 5,500, 6,000 and 6,500 cases failed the exact-once assertion: each two-node read returned 6,016 payload bytes and a 6,200-byte estimated working set before three pressure splits. The selected XML and numeric trace summary are alongside this note. This is a deliberate red diagnostic using a separately rebuilt test object and mixed incremental production objects; it is not a result for the unchanged 4,096-byte test or a clean same-tree build.

The legacy non-admission interface provides neither selected payload sizes nor a callback before allocation. Its existing post-read measurement cannot guarantee that an arbitrary result fits a smaller remaining budget. A safe implementation needs a way to admit or estimate before materialization, or an explicit contract for readers without that capability; simply retaining an oversized first read or discarding it and retrying cannot simultaneously establish the memory bound and exact-once I/O. This records a design constraint, not a claim that all possible implementations have been exhausted. The prior exact-once assertion and the stated budget remain in place.
