# MSVC debug PlanCache candidate

Run 41787248888, commit da4a6c2aaa3ff1770ef598693f0308d785e4045f, terminated during injected allocation 6/12 (16 bytes, alignment 8). Its symbolized stack goes from the allocation resource through MSVC's `_Container_proxy` allocation into `_Hash_vec` during `std::pmr::unordered_map` construction, and then to `std::terminate`. The official Microsoft STL `stl/inc/xhash` defines the allocator-taking `_Hash_vec` constructor `noexcept` even though debug iterator proxy allocation can throw. This is consistent with the observed failure; the exact runner's STL header version was not independently retrieved.

The candidate uses a PMR ordered tree with borrowed string-view keys only under MSVC iterator-debug mode, where its allocator-taking tree constructor is not `noexcept` in the upstream Microsoft STL implementation. Other configurations, including MSVC release, retain the existing hash index. List ownership, iterator targets, LRU order and transactional clone/insert/rollback are unchanged. Lookup complexity for Windows iterator-debug builds becomes O(log n) instead of expected O(1).

Linux validation forced the ordered branch in a temporary copied header and compiled the PlanCache test object, linking existing Linux core objects: 17/17 passed, including all injected allocation positions, rollback/retry, owner accounting, borrowed keys and LRU. The default Linux hash branch separately passed 17/17. XML files are in recovery/evidence/2026-11-04. This validates the index API and contracts on Linux, not MSVC iterator-proxy allocation or the complete tree. Windows native CI remains necessary. Other Windows and macOS budget, prefetch and RSS failures remain unresolved; the ASan-focused blind-rebase case passed in the run, but the full sanitizer gate did not pass.
