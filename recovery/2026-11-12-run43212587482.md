## A final-result lower bound, distinct from transient overlap

The complete gather fixture requires 300 one-entry public result maps under 262,144 bytes. Native layout reports Row=80, pair=392, alignment=8. MSVC's list-based hash node is 408 bytes (two pointers plus the aligned pair). Each nonempty map retains at least its sentinel and one data node. Therefore even excluding buckets, proxies, strings/list values, column metadata, alignment prefixes and every live source, the final result needs at least `300 * (80 + 2 * 408) = 268800` bytes, exceeding the quota by 6,656. The independent two-entry allocator probe reports exactly 1,384 structural bytes, matching `3*408 + 128 + 32`, which grounds this layout inference. A direct one-entry native measurement has not been collected; the retained JSON makes that distinction explicit.

Consequently this fixture's existing final representation cannot fit merely by shrinking a source batch or removing temporary moves. This is a specific constraint conflict, not a blanket claim that the Windows failures are test defects. The publicly exposed `ResultValue::VariantType` includes large physical entities and `getVariant()` returns it by const reference, so shrinking every hash node requires a deliberate representation/compatibility design and real billing for any new indirection. No such redesign or quota change is slipped into the BTree fix. The two-hop tests already passing and other remaining admission failures must still be assessed independently.
