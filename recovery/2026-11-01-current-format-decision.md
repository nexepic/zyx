# Reconstructed current format decision

The lost final numbers are not recoverable from the available evidence. The currently fetched implementation assigns a 16-bit segment/envelope version 5, 13, or 15 and a separate 16-bit superblock version 32, 40, or 42 according to build-time feature selectors. These builds do not all implement the same layout and capabilities. Reusing one of those values for the reconstructed layout would risk accepting files written by an incompatible experiment; giving distinct layouts the same value would also permit unsafe cross-build acceptance.

For the reconstructed single current layout, allocate segment/envelope version `0xF100` and superblock version `0xF101`. These are new reconstruction identifiers, not recovered historical version numbers. They are distinct from all six current identifiers above; the historical final identifier is unknown, so this is not proof against a collision with an otherwise undocumented historical build. There is no supported migration or old-format fallback. Unknown checksum-valid versions, including when present in either superblock slot, must be rejected rather than silently selecting a different known slot. Same-format torn-write recovery, snapshots, COW and public APIs remain required.

This decision is **not yet implemented or verified**. Before changing the constants, make the current ROW/column and completed SCAN layout and behavior independent of the old experimental build selectors, update initialization and all affected fixtures to use the same layout, remove legacy migration and fallback paths while retaining their nonlegacy behavioral coverage, and compile and test all configurations. Default, mixed, and SCAN test modes may exercise different operations, but binaries claiming the same version must understand the same durable layout. A version edit alone is unsafe and is not acceptance.

The minimal ROW creation contract has now been exercised: an isolated regression creates a writable ROW database, writes a node, closes, reopens and reads it. It passed the current default build and failed the current SCAN build at the explicit offline-construction guard (`row-contract-coherent.xml`, `row-contract-scan.xml`). The future unified layout therefore needs an authenticated per-file distinction between ordinary ROW authority, private SCAN BUILDING and completed SCAN authority. Completion must publish the authority transition atomically with its membership roots, and any SCAN admission must still require the measured whole-file 10% saving. The exact flag representation and dispatch have not been implemented or validated; forcing the existing SCAN build switch on is unsafe because its initialization guard and other compile-time paths currently assume every file is SCAN.

A further code-level constraint was checked in the reconstructed tree: the existing superblock has a `SCAN_BUILDING` flag but no explicit completed-SCAN flag, so absence of `SCAN_BUILDING` alone cannot distinguish a normal ROW file from a completed SCAN file. `RelocatableStorageBackend::open` currently invokes `VerifiedScanRoot::verifyComplete` for every writable file in a SCAN build before allocator recovery, while `initializeNew` refuses all creation in that build. In addition, the descriptor's root count and wire size differ (8 roots/192 bytes versus 9 roots/208 bytes), and graph mutation planning has compile-time SCAN branches. A unified implementation must therefore use an authenticated, validated file authority state and snapshot-specific dispatch throughout open, reads, mutation and recovery; a creation-only exception would permit later paths to assume membership that a ROW file does not have. The exact state encoding, atomic transition, and implementation remain open and untested.

## Proposed per-file authority encoding

For the new, single version only, use two mutually exclusive CRC-covered superblock flag bits: existing bit 2 denotes private `BUILDING`, and a newly assigned bit 3 denotes completed `SCAN`; neither bit denotes `ROW`. Both bits set is invalid and must fail superblock validation. Other unknown bits and all prior version numbers remain unsupported. This representation uses the existing CRC-covered flags word and requires no extra durable index or per-record growth. It is a reconstruction choice, not a recovered historical encoding.

Creation publishes ROW (neither bit); a private offline clone publishes BUILDING and is never openable through the public backend. The final admitted conversion batch must atomically clear BUILDING, set SCAN, and publish the verified descriptor and complete membership roots in the same superblock generation. A CRC-valid but semantically inconsistent state, including a SCAN state without a verifiably complete membership, must be rejected rather than treated as ROW. Empty SCAN databases need an explicitly tested complete-empty proof; a null membership root by itself must not be used to infer authority. The pre-existing whole-file admission check remains mandatory before the final publication. Recovery after a torn candidate chooses only a supported, valid slot and then applies that slot's state; a CRC-valid unknown-version slot is an error, not a fallback opportunity.

All selection is made from the pinned snapshot's superblock, not a process-global or compile-time selector: ROW routes through normal ROW/column behavior; SCAN requires verified membership for reads and maintains it on native graph mutations; BUILDING is limited to the offline builder. A pin of an older root retains its own authority and descriptor. Read-only and writable opens must validate the correct state before recovery mutates control pages. The new binary must always compile one descriptor layout with nine roots and 208 bytes, and all entrypoints that currently branch on `RSS_SCAN_PATH_FORMAT_ENABLED` or `ZYX_EXPERIMENTAL_SCAN_PATH_FORMAT` require individual classification as codec capability, per-snapshot behavior, or builder-only restriction. This paragraph is a design proposal; the state flag, dispatch, conversion, and associated tests are not implemented or validated yet. No existing user database is migrated by this work.
