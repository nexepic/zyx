Two and four actual threads share a single writable backend, each runs 100 operations (90 reads / 10 staged blind writes on its own node). A logical conflict can retry up to three times and is separately counted; latency includes staging, commit and any retries. Each run checks final rank 10 for every client and scans integrity. Six runs per configuration passed: no reported conflicts, retries or failures. Two clients: mean throughput 2863.765 ops/s, mean of per-run commit means 2.7941 ms and mean of per-run p95 4.0932 ms. Four: 3129.2717 ops/s, 4.9282 ms and 7.8889 ms respectively. These are small-graph direct-API measurements without parsing/network and have no comparable recovered historical baseline. They are not general performance claims. A prior paired cleanup comparison and its pilot failure are recorded separately.

In six single-thread pin-release runs, 32 node owner records remained while an old snapshot was held and all old values were readable. After releasing it, two actual delete-triggered cleanup sweeps cleared all 32 records in each run; all deleted nodes were invisible and integrity passed. File size was 1,572,864 bytes during the pin and at the end in each run. Record reuse is not physical file shrinkage or proof that accumulation is bounded for an indefinitely held pin. Separate fair-control evidence contains 12 rounds of 128 delete/create cycles and file sizes; that no-cleanup control is deliberately non-equivalent.

Run databases are created inside script-owned temporary directories and removed after checks. The results do not recreate historical source, logs, workloads, pinned32 baseline comparisons or the original dfd0e33d object.
