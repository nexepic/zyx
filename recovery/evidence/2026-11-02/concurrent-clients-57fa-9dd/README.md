# 2/4-client Release comparison: 57fa vs 9dd

This compares 57fa8e0723c0a3e94518a7c7cddfcca7646c5ae7 immediately before and 9dd38a8d after migration cleanup, not the unavailable historical dfd0e33d baseline and not an isolated fairness-reclamation comparison. Linux x86-64, Clang 19.1.7, -O3 -DNDEBUG, hooks off, one identical harness object compiled using 57fa public headers, two separately linked Release core archives, CPU affinity 0-3. Each run creates a fresh database with one owner per client. Two or four actual threads share one writable backend; each performs 100 operations (90 snapshot reads, 10 direct blind staged writes), then every final value is verified and integrity scanned. Six rounds per version/configuration are alternated AB/BA; all 24 runs exited successfully with zero reported failures. Concurrent tests were finished before timing.

The initial overlay-based pilot conflicted with the global snapshot fence and is retained as a failure, not counted. The measured direct stageMutationBatch follows the existing blind-owner regression contract. This small graph, low absolute duration, absence of parsing/network and limited samples differ materially from earlier historical workloads. The 95% paired t intervals use six runs and rounded output values; they do not establish general equivalence, broad speedup, or unfair-reclamation overhead. Refer to concurrent-formal.log, raw per-run logs and results.json. Formal per-run database files were created under script-owned temporary directories and removed after verification; no large database artifacts are included.
